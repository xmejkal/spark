# P215 bench, 2026-10-14: the first real flash, on the XIAO ESP32-C6

The PO flashed the button-light project onto his Seeed XIAO ESP32-C6 with `deploy.py --token ae7b-ae44`, in his own
terminal, on the Mac's own USB port (`/dev/cu.usbmodem101`, USB id 303a:1001, "USB JTAG/serial debug unit"). The
rows are AT131 to AT137 in [INDEX.md](INDEX.md). The council evaluates them next.

## What happened, in order

1. One Wokwi run of the scenario passed (09:37, about one free minute). The image did not change (`ae4419…`), and the
   log now names its three files.
2. `look.py` found the board, the same chip, and the flash size unknown, because the board record does not hold it.
   The look exits 2 for the unknown field. The token was `ae7b-ae44`.
3. The PO typed yes. esptool 5.5.0 erased the flash, wrote 4,194,304 bytes in 13.8 s, verified the hash, and
   reset the board through RTS.
4. Right after that, both mpremote steps failed: `fs cp` of `spark.json` and the hash read. Each gave "returned
   non-zero exit status 1". deploy.py said `ready unknown`, exited 2, wrote the board log and added the store record
   with the verdict `ready unknown`. This is honest, but it is not the pass.
5. Claude ran mpremote by hand: "could not enter raw repl", and the board sent no bytes at all (`b''`).
6. The PO unplugged the board and plugged it in again. A red LED then glowed, which did not glow before. mpremote
   still got no bytes.
7. With pyserial, Claude pulsed RTS. The board printed the ROM's boot text, `rst:0x15 (USB_UART_HPSYS),boot:0x1e
   (SPI_FAST_FLASH_BOOT)`, and then `ready`. So the image boots and the firmware runs. A Ctrl-C then gave the prompt of
   "MicroPython v1.29.0 on 2026-08-24; Seeed XIAO ESP32C6 with ESP32-C6".
8. The same Ctrl-C later gave nothing, under each safe DTR and RTS setting, and with or without a pause between
   Ctrl-C and Ctrl-A. It worked again when it came right after the boot text. These tests did not find the rule.
9. During one reset with the port open, macOS dropped the device: "[Errno 6] Device not configured". When it came
   back, mpremote answered at once.
10. Claude then ran the step 2 and step 3 code by hand: the facts file was written and read back, and the board read
    `ready seen`: the firmware printed `ready`, and its 3 files match the run that passed.

## What we know, and what we only think

- Known: the flash, the image, MicroPython, the firmware, the facts file and the ready check all work on this board.
- Known: right after esptool's reset, and after a replug, mpremote got no bytes from the board.
- Known: deploy.py kept only mpremote's exit status, not its error text, so its output could not say why.
- Thought, not proven: after a reset, the C6's own USB console takes input only once the USB device has come back
  cleanly. A host that opens the port too early, or holds it open across the reset, gets nothing.
- Unexplained: the red LED after the replug. The bench project's LED is red, and the firmware turns it off at start.
