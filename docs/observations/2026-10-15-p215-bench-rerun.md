Short version: the PO ran `deploy.py --token ae7b-ae44` on `~/Development/button-light` and the XIAO ESP32-C6 on
`/dev/cu.usbmodem1101`. esptool 5.5.0 erased, wrote 4,194,304 bytes and verified the hash. mpremote then got no bytes
("could not enter raw repl"), so ready was unknown. P244 (#255, PR #256) makes the log keep what the console said.

- The download-mode check ran, but did not read `waiting for download`, and deploy.py did not keep what it read.
- The store record failed: Claude gave `SPARK_HOME` as the spark repository, and spark refused to write inside a git
  work tree. Claude's mistake, not spark's.
- esptool warned: "Command 'erase_flash' is deprecated. Use 'erase-flash' instead." (the same for `write_flash`).
- The hint `repl,press` in the paste is a terminal line break: the code prints `repl, press`.
- Before the run, the PO asked whether Claude can type the yes itself. A probe that fakes a terminal was refused by
  Claude Code's auto mode ("Security Weaken"). From the code: the gate is `isatty` on stdin and stdout
  (`scripts/deploy_gate.py:42`), which a pipe fails and a pseudo-terminal passes.

## The second run, 00:44, after P244

The log now kept the console: `mode:DIO, clock div:2`, four `load:` lines, `entry 0x4086b910`, then `ready`. So the
board booted from flash, and the firmware ran. mpremote had asked while the board still restarted after esptool's
reset. P245 (#257) reads the board again when the console hears `ready`. The store record went to the real store.

## The third and fourth runs, 02:00 and 02:10, after P245

At 02:00 the console heard the boot and `ready`, and P245 read the board again. mpremote still said "could not enter
raw repl", so ready was unknown and the facts file was not written. After the run, Claude probed the board twice with
`mpremote exec`, which failed the same way. Then Claude opened the port with pyserial, DTR and RTS off. The board
restarted (boot text, then `ready`), and a Ctrl-C right after got no bytes back. The input buffer was empty after that
restart, so a full buffer (P238's proven cause) does not explain it. This open also restarted the board, which round 1
of P238 did not see in 4 opens.

The button-light firmware never read its console. With the PO's yes, its loop now reads the console without waiting and
drops what it reads, as blink-c6 does. The scenario passed in Wokwi, the look gave token `ae7b-08bc`, and at 02:10
deploy.py printed `ready seen`: the 3 files match, `spark.json` is on the board, and the store record says `ready seen`.
The bare board shows nothing after the pass, because this firmware drives an external LED on D8 and its breadboard is
not wired. The jumper test in the REPL was not run, because the PO has no wires.
