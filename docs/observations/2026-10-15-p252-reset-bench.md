# P252: what a reset does to pins and values on the XIAO ESP32-C6, 2026-10-15

A bench spike for P235's slice 0 (#263, D10). The PO watched the on-board LED, and Claude ran each mpremote 1.29
command from `~/Development/blink-c6` on `/dev/cu.usbmodem1101`. The board ran the button-light firmware (`main.py`
imports `light`, which drives an external LED pin, not the on-board one). Assumptions under test: A5 (what a reset
does to pins) and A10 (`resume` keeps values), from `docs/discovery/2026-10-15-p235-live-on-board/risks-and-tests.md`.

## Short version

- The on-board LED (GPIO15) is active low: it lights at 0. This was not in the board record (AT158 asked for it).
- An `exec` stops the firmware. A soft reset keeps the pin's value and does not start the firmware again.
- A hard reset (`mpremote reset`) restarts the chip and starts the firmware again. GPIO15 kept its value through it,
  both on and off.
- A value set by one call survives into the next only with `resume`. A plain `exec` soft-resets first and loses it.

| 3b | `exec` `value(1)`, 3 s, then `reset` | `led off`, exit 0 | the LED off, and off after the reset |
| 3b, check | `exec` `reset_cause()`, `ticks_ms()` | `5`, `30366` ms | — |
| 4 | `exec` `x = 42`, then `resume exec print(x)` | `x is 42` | — |
| 4, plain | `exec print(x)` | `NameError: name 'x' isn't defined` | — |
| 5 | `reset`, 4 s, then `resume exec` `'light' in sys.modules` | `True`, `ticks_ms 3332` | — |
| 5, soft | `soft-reset`, then `resume exec` the same | `False` | — |

Reset cause 5 is `machine.SOFT_RESET`. The ESP32 port reports a software restart (`machine.reset()`, which `mpremote
reset` calls) under that cause. The uptime shows that the chip restarted. Step 5 shows the firmware ran after the hard
reset: its module was loaded 3.3 s after the boot. A soft reset from mpremote's raw REPL does not run `main.py`.

## What it means for `reset_at_end` (Q5, Q9; the PO picks)

1. A hard reset at the end (recommended). The firmware runs again from boot, as after a power-on. Caveat from step 3:
   a pin that the try set and the firmware never sets keeps the try's value, as GPIO15 did. So P247 says which pins
   the try touched.
2. No reset. The firmware stays stopped, and the board waits at its REPL until a press of R or a replug. This is
   what `reach.py` does in P251, and it says so.
3. A soft reset. Rejected: it neither starts the firmware nor clears the pins.

## Open, not tested

- Why GPIO15 kept its value through a chip restart. GPIO15 is a strapping pin, so a reset with the LED on holds that
  strap low. The firmware still booted in step 5 (LED off at that reset), but a reset with the LED on was not checked
  for a normal boot.
- Whether a hard reset can leave the console silent (AT187). Step 5's `resume` reached the board each time (n = 2).
