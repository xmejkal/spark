# Design basis

Generated by `python3 tools/design_basis.py --write` from the code. Do not edit it: change the code, then run that command.

How to read this page:

- The moment of each phase and the unbuilt steps are hand-written, last on 2026-11-24.
- The phases, statuses, actors and Operations are read from the code.
- The offer kinds, their phases, labels and tells are read from `flow_codes.OFFER_KINDS`. Only each step is written in the tool.
- A key is `<group>:<name>`, and the group makes it unique.
- A phase reader is the code that reads one phase of a project. The usual actor of a phase is the one its reader names.
  In some states the guide names another actor, and `guide.now.by` holds the actual one.
- This page does not list which statuses each phase can show. Each phase reader decides that from the project's files.
- An offer key names a kind of offer, not one project's offer. Its label keeps its `%s` places.
- "From the page" says whether a click on the project page can send the offer. If it says no, you ask Claude in the chat.
- A tell is one sentence for Claude that names a job only Claude does. An offer with a tell is a chat offer, with no op.
- A status with no word is shown by its mark alone.
- The summary of an Operation is the one that `--describe` prints.

## Phases

| Key | Phase | Usual actor | Moment |
|---|---|---|---|
| `phase:idea` | idea | you | At the desk, in a chat with Claude: you say what you want the gadget to do. |
| `phase:needs` | needs | claude | At the desk: you read the needs Claude wrote from your goal and agree or change them. |
| `phase:parts` | parts | you | At the desk: you pick a part for each need, the parts you own first. |
| `phase:requirements` | requirements | claude | At the desk: Claude writes the parts list from your picks. You wait. |
| `phase:build` | build | claude | At the desk: spark builds the board files in seconds. You read what built and what was skipped. |
| `phase:breadboard` | breadboard | you | At the bench, hands busy, the USB cable out: you wire one step at a time, often from a phone. |
| `phase:firmware` | firmware | claude | At the desk, in the chat: you say what the gadget does, and Claude writes the firmware. |
| `phase:simulate` | simulate | your terminal | At the desk: you run the simulation in your terminal and read whether it passed. |
| `phase:deploy` | deploy | your terminal | At the bench, the board on USB: you run the deploy in your terminal and look at the board. |

## Operations

### idea

- `op:needs-drop`
  - Effects: writes. Data keys: none.
  - Summary: Drop a need and its pick from .spark/needs.json, and release only the holds of the dropped pick.
- `op:move-hold`
  - Effects: writes. Data keys: from_project, to_project, need, pick, released, written, projects.
  - Summary: move a part that one project holds to another: FROM keeps each need that picked it, with no pick, and TO picks it for NEED. Without --apply it says what each project loses and what goes out of date, and writes nothing

### sourcing

- `op:list`
  - Effects: none, it only reads. Data keys: parts.
  - Summary: every record a project can build with, and where it comes from
- `op:show`
  - Effects: none, it only reads. Data keys: record.
  - Summary: one record, wherever it lives, and its CONFLICT lines: on verified facts a problem (exit 1), on unverified ones an assumption
- `op:validate`
  - Effects: none, it only reads. Data keys: checked.
  - Summary: every record a project can build with, against the contract
- `op:signals`
  - Effects: none, it only reads. Data keys: signals.
  - Summary: the signals these parts ask for, as assign_pins.py input
- `op:unverified`
  - Effects: none, it only reads. Data keys: parts.
  - Summary: what nobody has checked about these parts, one assumption a fact
- `op:skeleton`
  - Effects: writes. Data keys: path, record, written.
  - Summary: write a record to fill in, to the project's parts/ (refused when any layer holds the id)
- `op:sources`
  - Effects: network. Data keys: part, sources.
  - Summary: ask every URL a record cites whether it answers
- `op:fetch`
  - Effects: network, writes. Data keys: documents, would_fetch, failed.
  - Summary: download the datasheets and images a record cites, into your store; never spark's library
- `op:find-documents`
  - Effects: network, writes. Data keys: record, page, top_view, drawing, declines, fetched, written.
  - Summary: find a DFRobot board's top view and dimension drawing on the maker's wiki page by its sku, keep them in your store and list them in the board's documents; it draws nothing, and a file the record keeps already is not fetched again
- `op:keep`
  - Effects: writes. Data keys: document, location_removed, written, record, key.
  - Summary: put a file you already have into your store; answers its documents entry, and with --part lists it in that record
- `op:keep-picture`
  - Effects: writes. Data keys: record, key, view, picture, document, written.
  - Summary: keep a picture of a part (an SVG in its frame, see --picture-frame) and name it in the part's record as its picture for a view
- `op:picture-frame`
  - Effects: none, it only reads. Data keys: svg, view_box, made_by, likeness.
  - Summary: the frame a part's picture is drawn on: an SVG in mm of its outline and its pads, from its record or its board's
- `op:read`
  - Effects: none, it only reads. Data keys: facts, pages_read.
  - Summary: read a datasheet page by page and stop where every --want fact is on a table row
- `op:kept`
  - Effects: none, it only reads. Data keys: found.
  - Summary: find a kept document by every word, with no network, and every fact resting on it
- `op:promote`
  - Effects: writes. Data keys: path, written.
  - Summary: catalog → the project's parts/, or the project's parts/ → the plugin's library
- `op:catalog`
  - Effects: none, it only reads. Data keys: records, broken.
  - Summary: every record research has kept, chosen or not
- `op:drawer`
  - Effects: none, it only reads. Data keys: entries.
  - Summary: what you own: each entry's key, label, count, the record it is, unsure, skip — 20 at a time
- `op:step`
  - Effects: writes. Data keys: step, written.
  - Summary: a spine step of a project starts now, in this Claude Code session — the cost line counts its transcript from here
- `op:drawer-set`
  - Effects: writes. Data keys: changes, questions, shelved.
  - Summary: set drawer entries from a JSON list in FILE (- for stdin): every write sets, never adds; with --project, an `is` may name a record in that project, such as one /spark:research just wrote; an entry may also say its about, description and tags
- `op:drawer-import`
  - Effects: writes. Data keys: changes, questions, shelved, smaller.
  - Summary: apply an importer's payload (FILE, or - for stdin) to the drawer: new entries, and counts by the re-import rule
- `op:function-set`
  - Effects: writes. Data keys: part, path, was, now, written, shelf_copy.
  - Summary: set what a part does — a JSON [{does, what}] in FILE (- for stdin) — in the record's own home (--project picks the project's copy); never spark's library
- `op:fact-set`
  - Effects: writes. Data keys: part, path, was, now, written, shelf_copy.
  - Summary: fill what a record owes — a JSON object of the facts the chain reads, or `facts` entries {value, verified, source} by name (a bench result is verified true and its source says who, when and how; a text in it has its control characters turned into a space and is cut at 1000 characters, and a key with a control character is refused), or its about, description and tags, or a board's onboard LED or button level, `pin_roles` {onboard_led|onboard_button: {active_level: {value, verified, source}}} (a board of the project's own, merged role by role), or a board's joined pads, `joined_pads` {value: [[pad, pad], ...], verified, source, why_it_matters, cites} (the groups of pads its maker's schematic joins inside the board, each pad in header_order; written to physical.header.joined_pads of a board of the project's own, replaced as a whole), or what the sheet reads, `legs` {pin of pin_order: how to tell the leg apart} (merged leg by leg), `host_requirements` [the lines the host board must meet] (replaced as a whole, like tags) and `short_name`, what the steps call the part, in FILE (- for stdin) — in the record's own home (--project picks the project's copy); never spark's library
- `op:features-set`
  - Effects: writes. Data keys: record, features, anchors, colour, written.
  - Summary: write a board's main features (chips, sockets, buttons, LEDs, holes, labels), measured in the pixels of the maker's top view that the record keeps, into its record in mm: scaled by the outline, turned so the USB end is at the bottom (never mirrored), checked against the record's pads and mounting holes; verified false, each with its source

### sourcing.research

- `op:research-part`
  - Effects: network, writes. Data keys: none.
  - Summary: Research one part record from ordered sources (P737): find the geometry gaps the chain needs, keep the documents a DFRobot module's wiki page lists, ask one question per gap that cites the kept drawing, and write the replies as facts.

### design

- `op:list-boards`
  - Effects: none, it only reads. Data keys: none.
  - Summary: Every board available to switch to.
- `op:audit`
  - Effects: none, it only reads. Data keys: layers, owed, broken, no_function, dangling, stops_at_footprint.
  - Summary: every record in every layer and every drawer link: what owes facts, what is broken
- `op:need`
  - Effects: none, it only reads. Data keys: need, vendor_order, found, drafts, catalog, more, matcher.
  - Summary: what you own and what spark knows for a need, before researching: the words against what each record (parts and boards, every layer) or drawer entry does, its tags, names and text, owned first (word-overlap); --matcher name-contains for the names alone
- `op:needs`
  - Effects: none, it only reads. Data keys: needs.
  - Summary: a project's needs: what each does, its condition, its mark
- `op:match`
  - Effects: none, it only reads. Data keys: needs.
  - Summary: each of a project's needs with the store's candidates: owned first, what each owes, each with its score and why; --matcher picks the matcher that ranks them; a board that serves a need through its own LED, button or display has `limits`, the sentences for what a passed run does not test of it, and so has a part whose record skips the simulation or names a stand-in
- `op:offer`
  - Effects: none, it only reads. Data keys: offer.
  - Summary: what one offer says of itself, for the chooser to read: a record's id or a drawer entry's key — about, description, tags, what it does, its names, power and size, each fact without its sources (the record's file holds them). --project reads the project's own records
- `op:requirements`
  - Effects: writes. Data keys: path, requirements, shelved, unplaced, kept, board_was, placeholder_outline, no_simulation_stance, unserved, no_supply, no_driver, no_receiver, written, unexplained, remove_key, previous.
  - Summary: the picks as the project's requirements.json: the board, and every part pick with a record — one that owes only its outline or its simulation is written with a warning, one that owes more is refused; a catalog one goes onto the shelf; what the file already holds stays; board_only when the board itself serves every need; it names each entry that spark wrote for a pick that is gone (data.unexplained), and removes them on the person's yes in --replies
- `op:tally`
  - Effects: none, it only reads. Data keys: picks, from_store, owned, cost, built, line, needs, needs_picked.
  - Summary: the cost line: the picks, how many came from the store (known to spark before the project: its library, your store, your projects) and how many you own, and what the project's steps cost
- `op:needs-set`
  - Effects: writes. Data keys: changes, written, basis_noted.
  - Summary: set a project's needs from a JSON list in FILE (- for stdin): every write sets, never adds. A write that defines a need, or [], also notes the goal and the must lines
- `op:pick`
  - Effects: writes. Data keys: project, picks, reserved, released, written.
  - Summary: set what each need picks (NEED=ID: a record, or a drawer entry) and reserve what you own of it — never past what another project holds; what it notes is under `notes`: a board given a need that its own part serves says what a run does not test of the part, and the other choice; a part whose record skips the simulation or names a stand-in says so

### build

- `op:build-board`
  - Effects: writes. Data keys: none.
  - Summary: The one thing that has to work: a module list in, a board that builds out.

### checks

- `op:check-design`
  - Effects: none, it only reads. Data keys: tool, status, unmeasured, resolved, results, project.
  - Summary: Run every deterministic check and answer once.

### bench

- `op:look`
  - Effects: none, it only reads. Data keys: none.
  - Summary: Read the board on USB without changing it, compare it with the project's board record, and print a token (P219).
- `op:deploy`
  - Effects: writes, deletes. Data keys: none.
  - Summary: Put the flash image onto the board: one that a passed run names (P192), or, with --no-simulation, firmware/ (P337).
- `op:issue-grant`
  - Effects: none, it only reads. Data keys: none.
  - Summary: Let Claude run code on one board for a time limit: one yes typed in your own terminal (P253).
- `op:check-grant`
  - Effects: none, it only reads. Data keys: none.
  - Summary: Say whether the board on USB has a live grant now: the check a later call makes (P253).
- `op:live`
  - Effects: none, it only reads. Data keys: none.
  - Summary: Run a short piece of code on the running board inside a grant, say whether the board ran it, and reset it (P247).
- `op:reach`
  - Effects: none, it only reads. Data keys: none.
  - Summary: Run one line on the board on USB, and cure it once when its USB output died at power-on: the PO's bench tool (P251).
- `op:show-bench`
  - Effects: none, it only reads. Data keys: boards.
  - Summary: each board on USB with its deploys, the projects that keep it and its grants, from spark's store; it opens no port
- `op:register-project`
  - Effects: writes. Data keys: registered, changed, launcher.
  - Summary: register a project that is not spark's, once, so that its own tool records its deploys with bench.py record; it touches no board
- `op:record-deploy`
  - Effects: writes. Data keys: entry, mac, device.
  - Summary: record one deploy of a registered project in spark's store, for the board on USB; it opens no port and reads nothing from the board
- `op:disallow-direct-flashing`
  - Effects: writes. Data keys: none.
  - Summary: keep the file grants/direct_flashing_disallowed in your store, at once and with no question

### flow

- `op:show-flow`
  - Effects: none, it only reads. Data keys: phases, stands_at, fingerprint, guide, deploy, name, title, stamp, artifact.
  - Summary: Say where a project stands, phase by phase from the idea to the deploy, and what each phase offers next (P825).
- `op:write-flow-page`
  - Effects: writes. Data keys: file, did, stands_at, phases, fingerprint, guide, artifact.
  - Summary: Write page.html in the project: each phase of the flow with a status word and a mark, and the project's pictures (P827).
- `op:run-request`
  - Effects: writes. Data keys: for, key, label, ran, status, mark, line, note, fingerprint.
  - Summary: Run the step the page asked for in .spark/page-request.json, a pick, the parts list or the build, only when spark offers it now and the project has not changed since the page was read (P829).
