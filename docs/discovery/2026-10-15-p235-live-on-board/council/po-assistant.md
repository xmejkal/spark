- POA-2 · mpremote is the tools-list job `board-shell`, found with `tools.find("board-shell", project)`. A spark setting can point that job at another tool. · E · scripts/deploy.py:147, 225, scripts/board_look.py:224 · supports only: "one tool per job, swappable" already holds for mpremote.
- POA-3 · spark has no serial monitor command and no live-try command. - POA-4 · ReadyCheck already is a short serial monitor. `run_code("import main", keep_running_for=20)` runs the firmware for 20 s and keeps what it printed as the board's log. · E · scripts/ready_check.py:55-60, scripts/board_connection.py:59 · supports only: a "monitor for N seconds" slice reuses this call. - POA-5 · The agent guide forbids the very move live tries need: "Never run mpremote by hand to turn an unknown into a pass." - POA-6 · Wokwi's simulation already reads the firmware's serial output in spark's scenario runs (the `ready` contract). - POA-7 · In the PO's tools: `mpremote` 1.29.0 is installed through pyenv at /Users/petr/.pyenv/shims/mpremote, MIT licence. `screen` is at /usr/bin/screen. pyserial 3.5 is importable. · E · `mpremote --version`, `pip show mpremote`, `command -v screen`, `python3 -c "import serial"` (2026-10-15) · supports only: nothing needs installing for a first slice.

### Existing first, outside (mpremote read at source; the rest are from model knowledge or the P218 council, marked)
- POA-9 · mpremote `run`: runs a local file from RAM without copying it to the filesystem, after a soft reset, and does not run the board's own `main.py`. · E · https://docs.micropython.org/en/latest/reference/mpremote.html read 2026-10-15 · supports only: "run a file live without a flash" is `mpremote run`. The file leaves no trace on the board.
- POA-10 · mpremote `mount`: makes a local folder visible to the board as `/remote`. It ends in the REPL, so it does not return in a script. The mount survives soft resets but needs manual action if `main.py` runs at start. · E · same URL, read 2026-10-15, plus brief P218 ★C14 (mpremote main.py:627-630) · supports only: mount suits a person at a terminal, not an agent call. `run` and `exec` return.
- POA-11 · mpremote `exec` runs code and prints the output. `--no-follow` returns at once. In 1.29.0 `exec`, `run` and `fs` soft-reset first. · E · same URL, mpremote/main.py `ensure_raw_repl` (lines 548-553, read 2026-10-15), P218 brief ★C14 · supports only: every live try restarts the firmware (this matches D29 "each try ends with a reset", but the reset comes first too). State in RAM is lost on each call.
- POA-12 · mpremote `repl` is described as "a terminal (or serial monitor)". It does not stop a running program, so Ctrl-C is needed first. It is interactive and needs a terminal, so an agent cannot use it. · E · same URL, read 2026-10-15 · supports only: the serial monitor job is `mpremote repl` for the person. For an agent it needs a bounded read (POA-4).
- POA-13 · mpremote's licence is MIT (the package metadata says so). The docs page states only the documentation copyright. · E · `pip show mpremote` (License: MIT), docs page read 2026-10-15 · supports only: free to call.
- POA-14 · mpremote needs the board to answer Ctrl-C to enter raw REPL. A firmware that never reads its console, or a board in ROM download mode, gives "could not enter raw repl". The bench hit both. · E · docs/guide/agents.md:577-578, p236-bench.md steps 3-5, p215-bench-rerun.md (third and fourth runs) · supports only: every live option rests on this. It failed in 4 of the 6 bench deploys I read about (p236: 2 of 3 deploys needed R; rerun: runs 1 to 3 gave unknown). Count is from the logs' prose, not a table.
- POA-15 · A search found a reported issue "repl unresponsive in ESP32-C6 on macOS" and a timing workaround (a sleep before the input flush in `enter_raw_repl`). The result was a search summary and an index of MicroPython issues, not the issue page. · H · https://notes.alelec.net/assets/mpy-triage/pair/1008.html (a third-party triage index, summary only, 2026-10-15) · supports only: the C6 on macOS may have a known mpremote fault. Unverified.
- POA-16 · Thonny: a GUI with a REPL, shell, file view and a MicroPython backend. MIT licence. Not a local CLI an agent can call. · H · model knowledge, and the P218 council's POJ-4/POJ-7 (docs/discovery/2026-10-13-p218-deploy-and-board/council/po-assistant-journeys.md) · supports only: Thonny is a person's tool, not a spark tool.
- POA-17 · belay: a Python library and CLI by Brian Pugh. Host functions marked with a decorator run on the board. Works over USB and WebREPL. Apache-2.0. What it guards (identity, confirmation) is not stated. It is not installed here. · E (snippets only) · P218 council POJ-37, https://github.com/BrianPugh/belay (search snippet, read 2026-10-13 by that lens) · supports only: it is a Python dependency, so it breaks "few tools". It runs behaviour on the board, which D29 allows only after a yes. I did not read the repository myself.
- POA-18 · A Claude plugin "fingerskier-micropython-claude-plugin" exposes an MCP server over mpremote: `list_devices, connect, device_info, list_files, read_file, write_file, delete_file, mkdir`. The snippet lists no `exec`. No identity check was seen. Licence unknown. · E (third-party listing only) · P218 council POJ-36 (claudepluginhub.com listing, not opened by that lens) and ★C15 in the P218 brief · supports only: AGENTS.md says a local CLI before an MCP server, and the plugin wraps the CLI spark already calls. P222 may read it (D30). I did not.
- POA-19 · pyserial `miniterm`: a terminal on a port, BSD-3-Clause (H, model knowledge). `screen /dev/cu.usbmodemXXXX 115200` is on the Mac already and is GPL (H). VS Code's serial monitor and Wokwi's serial monitor are GUI or simulator features. aiorepl is a MicroPython library that runs on the board (an async REPL), so it is firmware code, which AGENTS.md forbids spark to write. WebREPL is MicroPython's own, needs Wi-Fi and boot code on the board, one password, and mpremote cannot drive it. · H model knowledge for miniterm, screen, VS Code, aiorepl · E for WebREPL: P218 brief ★C13 (https://docs.micropython.org/en/latest/esp32/quickref.html read 2026-10-13) · supports only: pyserial/miniterm and screen open the port and toggle DTR/RTS. P215's rerun found a pyserial open restarts this C6 (POA-23). Outside tools do not remove that cost.

### Risks and assumptions
- POA-20 · Is the PO blocked without P235? No. He can run `mpremote repl`, `exec` and `run` himself today, and the bench passed with his hands and Claude's one-off port scripts. What is missing is a spark-gated, logged way for the agent to do the same. The PO has said he wants this (the #224 quote), so the want is D. The cost of waiting is not measured. · E for the workaround (p236-bench.md steps 6-7), D for the want (PO 2026-10-13 on #224), — for any cost of waiting · supports only: P235 is not urgent in the sense of a blocker. Its first slice should be small.
- POA-21 · Riskiest belief: "mpremote reaches a running board on this C6 reliably enough that a live try works first time." The logs say it does not today. The rerun's runs 1 to 3 gave "could not enter raw repl" even with the console heard, and the cause is open (P238 #235 round 1 did not explain it). If this fails, no option works, because every option here is mpremote or a port open. · E · p215-bench-rerun.md (third and fourth runs), p236-bench.md steps 3-9, docs/guide/agents.md:577 · supports only: ranking a "can we reach the board" check ahead of any new command.
- POA-22 · Cheapest test of POA-21: on the connected C6 with the P246-type board-only firmware that reads its console, run `mpremote exec "print(1)"` 10 times, each after a fresh `deploy.py` and each after a plain USB re-plug. Count answers. Pass line: the PO sets it (Q1). A stable board with a console-reading firmware likely passes (p236 step 7 worked). The open test is the state right after a flash and with a firmware that never reads its console. I did not run it (I change nothing). · H (a proposal) · supports only: this is cheaper than P222 and answers the same blocking doubt.
- POA-23 · Opening the port can itself restart the board. The rerun saw pyserial open with DTR and RTS off restart the C6 (boot text, then `ready`). A monitor that opens the port may therefore reset the firmware it wants to watch. · E · p215-bench-rerun.md third and fourth runs ("This open also restarted the board") · supports only: a serial monitor slice must say whether it resets the board. Unknown whether `mpremote repl` also does.
- POA-24 · Soft reset on every `exec`/`run`/`fs` (POA-11) means a live read of a running firmware's state (a pin value mid-loop, a counter) is not what `exec` gives. It gives the state after a restart. The job "read pins and sensors live" (Job 3) may need the firmware's own console output instead, or `mpremote resume` (the docs list it: "will not auto soft-reset"). · E · mpremote main.py:302-305, 548-553 (read 2026-10-15) · caveat: `resume` was never run on a board · supports only: Job 3 may be a different build than Job 1.
- POA-25 · D29 and D43 say live tries need one yes per session through P219's gate (look token plus the PO's own terminal). P242 (#249) is a separate card to let the AI deploy after a standing yes per board. If P242 ships first, the live session's yes may change shape. If it does not, an agent live try waits for a human in a terminal each session. · E · P218 brief D29, D43 (lines 171, 185), #249 comments ("yes to p242", 2026-10-14) · supports only: order P235's agent slice after, or with, P242's yes design.
- POA-26 · The gate checks isatty on stdin and stdout. Claude Code's auto mode refused a probe that fakes a terminal ("Security Weaken"). · E · p215-bench-rerun.md (short version, last bullet), scripts/deploy_gate.py:42 · supports only: an agent cannot supply the yes itself. A live-session slice needs the PO present at least once per session, unless P242 lands.
- POA-27 · Safety: free `exec` on the bench can drive a pin the wrong way. D29's own caveat says pins.py holds no direction. · E · P218 brief D29 line 171 · supports only: a "Job 3 read pins" slice may stay read-only (`Pin.value()`) by convention, but spark cannot enforce it with free `exec`.

### Assumptions each option needs
- POA-28 · A live REPL try over USB (Job 1) pays off only if: (a) mpremote reaches the board (POA-21), (b) a soft reset per try is acceptable to the PO (POA-11, D29), (c) the PO prefers a spark command to typing `mpremote exec` himself. (c) is untested. · H · my reading of POA-8, 11, 21 · supports only: Job 1.
- POA-29 · A serial monitor (Job 2) pays off only if: (a) a bounded read (like ReadyCheck's) is what the PO wants, not a long follow, (b) opening does not reset the firmware (POA-23), (c) it adds something over `mpremote repl`/`screen`, which exist. It fits Job 2 best as "what the board printed in N s, kept as a log", which the deploy already writes under sim/runs/board/. · H · POA-4, 12, 23; deploy log path from docs/guide/agents.md:579 · supports only: Job 2.
- POA-30 · Running a file without a flash (Job 1 variant) pays off only if: the file runs the project's real `main.py` imports (`pins.py`, `blink.py`) and `mpremote run` finds them. `run` executes one file from RAM, and the other project files must already be on the board, or `mount` must serve them. `mount` does not return (POA-10). · E for run/mount behaviour (POA-9, 10), H for the import question · supports only: this option may be weaker than it sounds. A one-file test script works. A whole project does not, without a flash or a mount.
- POA-31 · Debugging (Job 3) pays off only if the PO has wires and parts to debug. He has none now ("i dont have any cablues"). The jumper test was not run. · E · p215-bench-rerun.md last paragraph, #260 body · supports only: Job 3 cannot be proven at the bench today. Any claim would stay H.
- POA-32 · WebREPL and OTA need Wi-Fi and boot code on the board, which is behaviour spark does not write. They were set as a later discovery. · E · P218 brief D31 (line 173), ★C13 (line 58), no-go at line 101 · supports only: keep out of the first slice.

### Pre-mortem: six months after the first slice shipped, it failed. Why?
- POA-37 · The command worked in tests and failed on the bench, because mpremote could not enter raw REPL right after a flash or with a firmware that does not read its console (POA-14, 21). The PO went back to typing in a terminal. · H (built from E in POA-14, 21) · supports only: test reach first.
- POA-38 · The slice wrapped one mpremote line and added no gate value over what the PO types by hand (POA-8, 28c). Nobody used it. · H · supports only: ask whether the PO would use it (Q2).
- POA-39 · The monitor reset the board when it opened the port, so it hid the bug it was meant to show (POA-23). · H (from E POA-23) · supports only: test an open with and without reset.
- POA-40 · The yes per session (D29, D43) cost a terminal visit each time, and the agent live-try job stayed manual until P242 landed (POA-25, 26). · H · supports only: order against P242.
- POA-41 · A live try with free `exec` drove a pin the wrong way and hurt a part, and the PO stopped trusting the agent on the board (POA-27). · H (D29 names the caveat) · supports only: Job 3 and 4 slices need a read-only default.
- POA-42 · A later toolchain (Arduino, P221) made the REPL story moot for half the projects, and the slice was MicroPython-only (the scope excludes it). · H · supports only: low weight for the first slice, since spark serves MicroPython now (VISION non-goal "Arduino or ESP-IDF before a design pulls them").
