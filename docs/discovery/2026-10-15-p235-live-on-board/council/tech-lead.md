# P235 live on the board: tech lead report (feasibility, direction, electronics-firmware:physics)

Read 2026-10-15. Nothing was run against a board and no serial port was opened. mpremote 1.29.0 was read as installed source and its `--help` was run (it touches no board). Tags: E has a pointer, H says where it comes from, D says who and when. A dash is an unknown. I decide nothing.

Short version for the reader:
- The core already has most of what slice (a) and (c) need. `BoardConnection.run_code` runs any code string through `mpremote exec`. A file run needs no new method.
- The gate is the part that does not fit. `require_open_gate` is written for an erase, and a live session needs a grant that lasts across many separate command calls.
- Everything depends on one thing the bench has not settled: whether a Ctrl-C reliably reaches the running firmware. P238 says it does not on the XIAO C6 when the firmware never reads its console. That, plus what "ends with a reset" means, is what P222 must answer first.
- The physics: a live `exec` can drive any pin, including the USB pins GPIO12 and GPIO13. A soft reset does not release a driven pin. The board record names no USB or flash pin roles.

## Findings

### Feasibility and direction (TL)

**TL-1 · The existing core already covers a one-shot live try.** `BoardConnection.run_code(code, keep_running_for)` runs `mpremote exec <code>`. It raises `BoardUnreachableError` for mpremote's own failures and `BoardCodeError` when the board's code raised. `copy_to_board`, `read_file` and `repl_command` sit beside it. ReadyCheck and FactsFile already use it, and `FakeBoardConnection` already fakes it. A live try needs a new class that calls `run_code`, not a change to the adapter. · E · `scripts/board_connection.py` (the whole file, 93 lines), `scripts/ready_check.py:check`, `tests/fakes.py:FakeBoardConnection` · supports: slice (a) is small to build and testable without a board.

**TL-2 · Every spark call is a separate mpremote process, and each one soft-resets the board first.** In mpremote, `State._auto_soft_reset` starts True, and the first `exec`, `run` or `fs` calls `enter_raw_repl(soft_reset=True)`. The next process starts again at True. So a "session" made of several `run_code` calls has no shared Python state between tries, and each try also restarts the interpreter. `mpremote resume` before the command turns the soft reset off, so globals set by an earlier try can survive. No test or bench ran this. · E · mpremote `main.py` `State.ensure_raw_repl` (about line 536-552), `commands.py:530-531` `do_resume`, `transport_serial.py:178-212` `enter_raw_repl` · caveat: that `resume` keeps globals is H (MicroPython behaviour, not run) · supports: whether a try can build on the last one. Answerable by a short bench rung, not by code alone.

**TL-3 · Whether any live try works at all depends on a Ctrl-C reaching the firmware, and the bench shows it is not reliable.** `enter_raw_repl` first writes `\r\x03` and then waits for the raw REPL prompt, even with `soft_reset=False`. P238 proved one cause of failure: the board reads only as many USB bytes as its input buffer has room for, and looks for Ctrl-C only among the bytes it read. A firmware that never reads its console fills the buffer and Ctrl-C never gets through. The same sequence gave a prompt in one run and nothing in the next. P215's re-run saw mpremote fail with "could not enter raw repl" on button-light (it never read its console) and succeed after the firmware was changed to drain the console. · E · `docs/observations/2026-10-14-p238-spike/finding.md` ("Proven", "Not stable"), `docs/observations/2026-10-15-p215-bench-rerun.md` ("The third and fourth runs"), mpremote `transport_serial.py:178-210` · supports: this is the first thing P222 must settle. A live-try slice built before it may fail on boards whose firmware is chatty or deaf.

**TL-4 · The ReadyCheck pattern shows how a try on a never-ending firmware must be shaped.** `exec "import main"` never returns when `main` loops forever, so `keep_running_for` lets `subprocess` time out and keeps the stdout read so far. When the subprocess is killed, mpremote's `do_disconnect` (which sends Ctrl-B to leave raw REPL) does not run. A clean mpremote exit does run it and leaves the board in the friendly REPL with the firmware stopped. In both cases the firmware does not restart until something resets the board. What state the board is left in after a kill was not measured. · E · `scripts/board_connection.py:run_code`, `scripts/ready_check.py:READY_WAIT_S`, mpremote `commands.py:73-90` · caveat: the state after a kill is — · supports: "each try ends with a reset" (D29) is also what restarts the gadget's own program.

**TL-5 · Slice (a), a live `exec` through the gate: the gate needs real change.** `require_open_gate(report, token, consent, image)` hard-codes the erase: the question is "erase ALL of this board's flash and write %s?", the token's second half is the image, and `report.stops` and `report.warnings` come from the flash look. A live session has no image and no erase. D43 says it goes through the same gate, the look's token and a terminal yes. That needs the question and the scope to become arguments, and the image half of the token to be optional or replaced. `ConsentStrategy` and `TerminalConsentStrategy` can be reused as they are. · E · `scripts/deploy_gate.py:49-68`, D43 and D18 in `docs/discovery/2026-10-13-p218-deploy-and-board/brief.md:160,185` · supports: the gate change is the largest piece of slice (a), larger than the exec itself.

**TL-6 · The look is a hard reset of the board, so every gated live session starts by stopping the gadget.** `look.py` prints "the board restarts while it is read" because `esptool flash_id` ends with a hard reset. D43 puts the look's token at the start of a live session. So the session start costs an esptool reset, and the bench shows an esptool reset can leave this chip in download mode (see PHY-5). It also needs the port free: esptool failed with "Could not exclusively lock port" while the PO's mpremote held it. · E · `scripts/look.py:RESTART`, `docs/observations/2026-10-14-p238-spike/finding.md` round 2 item 5, `docs/discovery/2026-10-13-p218-deploy-and-board/brief.md` ★C8 · supports: whether the live gate needs the full look every time, or may reuse a recent token, is a question for the decider (Q-TL-2).

**TL-7 · A live "session" has no home today. The CLI is stateless per call, so the yes must be stored.** The yes is typed in the person's own terminal (`isatty` on stdin and stdout), and Claude then issues many Bash calls. Nothing connects the two unless a grant is written somewhere: a record with the board's MAC, a start time, an expiry and a scope. The nearest existing thing is P242 (#249), the PO's standing yes per board by MAC, kept in his store and read by a new ConsentStrategy subclass. The store already keeps `boards/<MAC>.json` with each deploy and "whose yes" (`record_deploy`). A session grant is a short-lived cousin of that standing yes. D29 says the session ends with a reset. D29 does not say what ends the grant if Claude never sends the reset. · E · `scripts/deploy_gate.py:TerminalConsentStrategy`, `scripts/board_facts.py:record_deploy`, #249 comments ("The PO, 2026-10-14: yes to p242") · D · D29, D43 (the PO, 2026-10-13) · supports: the design question is where the grant lives and how it expires. It is not an mpremote question.

**TL-8 · Slice (b), a serial monitor: spark has a pyserial reader, but only for a fixed 2 s and only for download mode.** `download_mode.READ_CONSOLE` opens the port with DTR and RTS off through mpremote's own Python and prints what it hears for N seconds. It is the right seed for a bounded monitor (`--seconds N`, text or `--json`). There is no spark command called monitor. Streaming forever fits a person but not an agent that needs a bounded answer. `repl_command()` already gives a person the live view (mpremote repl). The monitor also cannot run beside mpremote or esptool (exclusive port lock). · E · `scripts/download_mode.py:READ_CONSOLE`, `scripts/board_connection.py:repl_command`, `docs/observations/2026-10-14-p238-spike/finding.md` round 2 item 5 · supports: smallest monitor is a bounded read class beside `DownloadModeProbe`, sharing its read code. It is about one small class plus a thin `monitor.py`.

**TL-9 · A monitor is lossy and cannot prove a negative.** MicroPython drops USB-Serial-JTAG output that the computer does not take within 200 ms (`usb_serial_jtag_tx_strn`). Opening the port may also restart the chip (PHY-6). So a monitor that opens late misses the boot text, and one that opens restarts the thing it watches. Neither was measured for how often. · E · `docs/observations/2026-10-14-p238-spike/finding.md` ("Proven") · supports: "the firmware printed nothing" must read as unknown, not as a fault. This matches the repository's "could-not-run is not a pass" rule (`docs/guide/agents.md`).

**TL-10 · Slice (c), running a file without a flash: `mpremote run` is the smallest, a copy of one file is the riskiest.**
- `mpremote run f.py` reads the local file and sends it as the same raw-REPL `exec`. Nothing is written to the board's flash. It is the same call as `run_code` with the file's text, so `BoardConnection` needs no new method for a first version, though a `run_file` would be clearer.
- `mpremote mount <dir>` mounts a local folder as `/remote` and does not return on its own. It ends in the REPL unless chained with `run`, which is why P218 marked it as not returning. It needs the mpremote process to stay alive while the code runs.
- A copy of one file (`fs cp`, already `copy_to_board`) writes to the board's filesystem. That departs from D33's "files on the board match the passed run's hashes". After a copy ReadyCheck would say `ready not seen` for that file, and `spark.json` would describe a board that no longer matches it.
· E · mpremote `commands.py:482-522`, `scripts/board_connection.py:copy_to_board`, `scripts/ready_check.py`, `docs/discovery/2026-10-13-p218-deploy-and-board/brief.md` ★C11 and ★C14 · caveat: none of the three ran on a board here · supports: the order run, then mount, then copy, by how far each departs from "the passed artefact is the whole image".

**TL-11 · Live code is code that never passed the simulation.** AGENTS.md says spark exports facts and never behaviour, and "the conversation writes the firmware". A file run is the conversation's code, not spark's, so the rule holds. The rule that matters for the design is UC7 step 7: live code must never be taken for firmware, and a code change goes back through P215's flash. That is a rule about what the command prints and records, such as "this ran on the board and is not on it afterwards". It is not a technical limit. · E · `AGENTS.md` (Principles), `docs/discovery/2026-10-13-p218-deploy-and-board/jobs-and-journeys.md:277` · supports: the live command's output should say what stayed changed. Which facts to list is for the decider.

**TL-12 · Slice (d), reading pins and sensors live, is a code snippet, and the open question is who owns the snippet.** The facts a read needs already exist: the board record's `pins` (silkscreen label to GPIO) and the project's `pins.py`. The read itself is `machine.Pin(n).value()` or an ADC read. If spark ships a fixed snippet, it is code that runs on the board, which sits near the "never behaviour" line even though it is a generic read, not firmware logic. If Claude writes the snippet in the conversation, the core only supplies the pin facts and the gate. `pins.py` carries no direction (★C16), so spark cannot tell a safe read from a drive by the pin map alone. · E · `boards/xiao-esp32-c6.json` (`pins`), `~/Development/blink-c6/firmware/pins.py`, `docs/discovery/2026-10-13-p218-deploy-and-board/brief.md` ★C16 · D · D29 chose free `exec`, not narrow verbs (the PO, 2026-10-13) · supports: Q-TL-3.

**TL-13 · Slice (e), WebREPL and OTA: they need code on the board that spark does not write, so they are the least fit for the direction.** WebREPL starts from boot code (`webrepl.start()` plus a Wi-Fi join) and holds one password for all interfaces. mpremote's `connect` takes a device name, path, `id:` or `port:`, and its help names no network transport, so `mpremote` cannot drive WebREPL. `webrepl_cli.py` only gets and puts files. The kept partition table has no OTA slot (★C12), so OTA means a new layout and an image the simulator has not passed. Both need a stored secret, which the store has no place for today. The brief already puts the Wi-Fi slices later (D1, D31). · E · `python3 -m mpremote connect --help` (run 2026-10-15), `docs/discovery/2026-10-13-p218-deploy-and-board/brief.md` ★C12 and ★C13 · caveat: ★C13 and ★C12 were not re-read at their sources · supports: nothing for the first slice. Keep (e) out of it.

**TL-14 · The new code fits "one core, thin interfaces" if it follows the shape the deploy area already has.**

· E · `docs/guide/developing.md:219-267` ("Patterns and names in spark's core"), `scripts/outcomes.py:68` `envelope`, `/usr/bin/grep -n json scripts/look.py scripts/deploy.py` found none · supports: every slice except (e) fits. The gate generalization (TL-5) is the one real design edit.

### Physics (PHY)

**PHY-1 · Pin current ratings.** The ESP32-C6 datasheet gives the high-level source current IOH = 40 mA typ (VDD 3.3 V, VOH >= 2.64 V, PAD_DRIVER = 3) and the low-level sink current IOL = 28 mA typ (VOL = 0.495 V, PAD_DRIVER = 3). Absolute maximum for the cumulative IO output current is 1000 mA max, and there is no per-pin absolute maximum in the pages read. Default drive strength is 20 mA for all pins except GPIO12 and GPIO13 at 40 mA. · E · datasheet-typ and datasheet-max · https://documentation.espressif.com/esp32-c6_datasheet_en.html page 65 (Table 5-4), page 64 (Table 5-1), page 17 (Table 2-2 note 3), read 2026-10-15 · caveat: the datasheet is for the chip, not the Seeed XIAO board · supports: what a wrong output can source or sink.

**PHY-2 · A pin driven wrong against a hard short or an opposing driver.** Formula, with the datasheet-typ points treated as a linear on-resistance (a crude model): R_high = (3.3 V − 2.64 V) / 0.040 A = 16.5 ohm. R_low = 0.495 V / 0.028 A = 17.7 ohm. Two opposing outputs shorted on a breadboard: I = 3.3 V / (16.5 + 17.7) ohm = about 97 mA (calculated, python run 2026-10-15). An LED with no series resistor at an assumed 2.0 V forward drop: (3.3 − 2.0) / 16.5 = about 79 mA (calculated, the 2.0 V is an assumption, not a read value). Both are well above the typical 40 mA and 28 mA points. The same datasheet footnote states that the product stayed fully functional after all IO pins were pulled high while connected to ground for 24 consecutive hours at 25 degC. · E (inputs) and calculated (result) · same datasheet pages as PHY-1 · caveat: the linear model ignores that the driver saturates, so the real current is lower. The footnote is a chip test on the bare chip at 25 degC, not a breadboard with a module. It does not show wear, heating of the module, or the USB host's limit · cheapest rung to settle it: a bench read of the pin's current into a 330 ohm resistor and a meter (measured). It cannot show lifetime damage or what a connected module's own output does. · supports: the size of the harm D29 names.

**PHY-3 · Which GPIOs are restricted, and which of them a live try can reach on the XIAO C6.** The XIAO C6 board record lists header GPIOs 0, 1, 2, 16, 17, 18, 19, 20, 21, 22, 23 (from its `pins`), plus GPIO15 as the on-board LED. Espressif's restrictions (https://documentation.espressif.com/esp32-c6_datasheet_en.html pages 24-25, and https://docs.espressif.com/projects/esp-idf/en/latest/esp32c6/api-reference/peripherals/gpio.html, read 2026-10-15):
- Strapping: GPIO4, GPIO5, GPIO8, GPIO9, GPIO15. The record agrees (`pin_roles.strapping`).
- USB Serial/JTAG: GPIO12 (D-) and GPIO13 (D+). The ESP-IDF page says if they are reconfigured as normal GPIOs, USB-JTAG functionality is disabled. A live `Pin(12, Pin.OUT)` would drop the very port the session runs on.
- JTAG: GPIO4 to GPIO7.
- UART0: GPIO16 (TX) and GPIO17 (RX). Both are on the XIAO header. The record names only GPIO16 (`console_uart`).
- SPI flash: GPIO24 to GPIO30 (SPI0/1), "not recommended for other uses". GPIO27 is also VDD_SPI.
The board record's `pin_roles` has strapping, console_uart, onboard_led, spi and i2c. It has no USB, JTAG or flash role, so a guard for those would need new facts. `exec` is free (D29), so no guard sits between a try and these pins today. GPIO12, GPIO13 and GPIO24-30 are not on the XIAO header, but code can still address them. · E · datasheet text, ESP-IDF doc, `boards/xiao-esp32-c6.json` · supports: whether the live scope needs a deny list, and which facts to add (records grow by need).

**PHY-4 · A soft reset probably does not release a driven pin, so "ends with a reset" must be chosen with care.** A web search summary of the MicroPython reset docs says Pin modes and output levels are not reset on most ports by `machine.soft_reset()` or Ctrl-D, and only `Pin.irq()` is always reset. The mpremote soft-reset on first exec, and Ctrl-C to stop the firmware, are the same kind. So an output left high by a try stays high through the next try. A motor or relay driver input driven on stays on while the firmware is stopped. A hard reset (`machine.reset()`, the `mpremote reset` shortcut) returns the pins to their reset state. That one also re-enumerates USB (PHY-7). · H · https://docs.micropython.org/en/latest/reference/reset_boot.html (seen in a search result summary only, the page was not opened, and the ESP32 port was not named in the summary) · cheapest rung: on the bare board, set the on-board LED (GPIO15) with `Pin(15, Pin.OUT).value(1)` through exec, soft-reset, and see whether the LED stays lit. This settles the ESP32-C6 port with no wires. It cannot show the state of a pin with an external load. · supports: what D29's reset must be. The PO decides.

**PHY-5 · Download mode after an esptool reset: Espressif's text and the bench logs fit each other, but the bench logs disagree with each other.**
- Espressif, esptool troubleshooting: "With USB-Serial/JTAG ... the USB-Serial/JTAG peripheral can only trigger a core reset, which does not re-sample the state of the boot strapping pin. As a result ... the chip stays in download mode". The fix is `--after watchdog-reset`. https://docs.espressif.com/projects/esptool/en/latest/esp32c6/troubleshooting.html, read 2026-10-15. · E
- Espressif TRM 32.3: RTS=1, DTR=0 resets the chip. RTS=0, DTR=1 sets the download-mode flag. If the flag is set when the chip resets, it reboots into download mode. https://documentation.espressif.com/esp32-c6_technical_reference_manual_en.html page 1029, read 2026-10-15. · E (stated)
- P236 bench step 5: "So esptool's reset alone leaves this chip in download mode." Its later "cause" section softens this: the chip was already in download mode before esptool ran. `docs/observations/2026-10-14-p236-bench.md` steps 5 and 9 and "The cause".
- P238 round 1, same day: "after esptool's reset, the ROM did not answer esptool with `--before no-reset`, so the board was not waiting in download mode." `docs/observations/2026-10-14-p238-spike/finding.md` "Proven".
- P238 round 2: "15 of 15 esptool resets booted the firmware when nothing else held the port. Download mode came only when the chip was already in it, or when a probe opened the port at a reset."
Round 2 and Espressif's text agree: a chip already in download mode stays there. Step 5 of the P236 log read as a general claim disagrees with round 2, and the P236 log's own "cause" section moves to round 2's reading. · E · supports: a gated live session that starts with an esptool look can strand a chip that was in download mode before. The existing `DownloadModeProbe` already asks for a press of R.

**PHY-6 · Opening the port may restart the chip, and the bench logs disagree.**
- P238 round 1 (Proven): "opening the port does not restart the board (4 opens, no boot text)."
- P238 round 2 (item 4): "Even after `--after no-reset`, the chip restarted, so opening the port restarted it", with DTR and RTS off.
- P215 re-run, 02:00: "This open also restarted the board, which round 1 of P238 did not see in 4 opens."
- Espressif says (TRM 32.3) the line states set by the host drive reset and the download flag, but which states a macOS open leaves was not measured: "the exact sequence was not measured here" (`finding.md`).
So the logs disagree: 4 opens in round 1 saw no restart, and the round 2 opens and the 02:00 open of the re-run saw one. The later logs name the restart outright, so I read them as the stronger evidence. A monitor that opens the port may restart the gadget it watches, and it can also catch the ROM boot text, which is a feature. · E · supports: the monitor's honest description ("opening the port may restart the board"). Rung: log pyserial `dtr`/`rts` after open and read the ROM line `rst:0x.. boot:0x..` on each of 20 opens. That shows the boot-mode bits per open. It cannot show other operating systems or other drivers.

**PHY-7 · A hard reset may change or drop the port on macOS.** P238 round 1: "During two resets with the port open, macOS dropped the device ('Device not configured')." `download_mode.wait_for_reset` only watches for the same port name coming back, and `NO_RESET` already warns the port may return under another name. `mpremote reset` runs `time.sleep_ms(100); machine.reset()` after an `exec`, which closes the USB device. A live session that ends every try with a hard reset will need to find the board again (by id or MAC, ★C9 is H for MicroPython, not measured). · E (log and code) · `docs/observations/2026-10-14-p238-spike/finding.md` "Not stable", `scripts/download_mode.py:NO_RESET,wait_for_reset`, mpremote `main.py` "reset" expansion · caveat: how often the name changes is — · supports: the cost of choosing a hard reset in PHY-4.

**PHY-8 · Ctrl-C leaves outputs as they were.** Stopping the firmware (what every `exec` does first) halts the program and not the pins. For the boards in use (an LED) the harm is nil. For the RC-car direction in memory (motors) it is not nil, because a driver input left high keeps the load on while no code runs. That follows from PHY-4 and is H (reasoned, no board with a load was tested). · H · PHY-4, memory `spark-north-star-rc-cars.md` · supports: a note in the live session's end message, "pins stay as the last try left them", and a possible rule for boards with loads. Not needed for the bare XIAO.

**PHY-9 · The XIAO board has pins and parts the record does not know about.** My own knowledge, not read here, says the Seeed XIAO ESP32-C6 uses GPIO3 and GPIO14 for an on-board RF switch (enable and antenna select). The record's `pins` has no entry for GPIO3 or GPIO14. Driving them wrongly could cut the radio, which matters only to the Wi-Fi slice (e). · H · the tech lead's memory of Seeed's wiki, not read this session · supports: nothing for the USB slice. It belongs to the research of the Wi-Fi slice and needs the Seeed schematic.
