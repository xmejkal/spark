## 1. Findings

### Q1. The check before any erase or write

- TLJ-1 · Four board states decide what a check can read. (A) MicroPython running, with a port. (B) the chip in its ROM bootloader (waiting for download). (C) other firmware running (Arduino, a vendor image, a blank flash), possibly with a USB port and possibly not. (D) no port at all (a power-only cable, a chip in deep sleep, native USB switched off by firmware). `mpremote` works only in A. `esptool` works in A, B and C when the chip can be put into download mode (on a USB-Serial/JTAG board automatically, E https://docs.espressif.com/projects/esp-idf/en/latest/esp32s3/api-guides/usb-serial-jtag-console.html, 2026-10-13; or by BOOT then RESET, E DFRobot wiki FAQ, `council/tech-lead.md` PHYS-2). In D nothing can be read. A check result for state D is "unknown, cannot be read" for every field, and a deploy that treats unknown as a pass breaks `docs/guide/agents.md` "a could-not-run is not a pass" (E `AGENTS.md`). · E for the tools' scopes, H for the four-state split (Claude's reading) · supports only: the split as a way to describe results.
- TLJ-2 · Reads in the order of least contact. Each row: tool · what it returns · cost · whether the board is left as it was.

| step | tool and command | returns | time | board afterwards |
| --- | --- | --- | --- | --- |
| 0 | host-side port list: `mpremote devs` (E: lists port, USB serial number, VID:PID, maker, product; run locally 2026-10-13, columns as printed) | which ports exist, their USB VID:PID and serial | — (milliseconds, H; not timed) | untouched: no byte is sent to a board (H: it reads the host's USB table) |
| 1 | `mpremote connect <port> exec "..."` | MicroPython build (`sys.implementation`, `os.uname()`), `machine.unique_id()`, flash size, heap, partitions, `os.listdir`, a file's content | — (a second or two, H; not timed) | not reset. It interrupts a running program (E mpremote docs, TL-9). main.py stays stopped until a soft or hard reset. The gadget is idle at the REPL, not running its loop |
| 2 | `esptool --port <p> flash-id` / `chip-id` / `read-mac` / `get-security-info` | chip name and revision, eFuse features (embedded flash/PSRAM), MAC, flash maker/device id/size, security state (E TL-3 and esptool docs) | — (connect plus stub upload, a few seconds, H; not timed) | the chip is reset into the ROM bootloader. By default esptool ends with a hard reset (E: `--after {hard_reset,...}` in the installed v3.3 `--help`; default in 5.5.0 —). So main.py restarts. Pins pass through the bootloader's reset state first. With `--after no-reset` the chip stays in the bootloader: it must then be reset by hand if the person says no |
| 3 | `esptool ... read-flash 0 <size> <file>` (a backup) | the flash bytes | calculated upper bound 16,777,216 B × 10 bit / 460,800 baud = 364 s if the port were a 460,800-baud UART (inputs: 16 MiB stated, 10 bits per byte H, 460,800 stated by the MicroPython page's example); native USB does not use the baud rate (H) | same as step 2 |

  · E for the tool list and the `--after` option, H and — as marked · supports only: the table's own cells. Time per step is — until the bench measures it (PHYS-style: measured).
- TLJ-3 · Why the order. Step 0 touches nothing and can already name how many boards there are (Q6) and which USB mode each shows (VID:PID, TLJ-27). Step 1 is the only read that sees the person's work (which project, which files) and it does not reset the chip. Step 2 is the only read of the chip itself and the only one that works in states B and C, but it restarts the gadget. So an order of 0, 1, 2 reads the cheapest and least intrusive facts first and reaches the invasive one only for what the first two cannot say. A second order (2 first) is shorter in one case: a board that is blank or in the bootloader has nothing for step 1 to read. A check that goes 0, then 1 if a MicroPython port answers, then 2, covers both. Whether `mpremote exec` stalls on a port that holds non-MicroPython firmware is — (not read). It needs a timeout. · H · Claude's ordering from the table · supports only: a sequence to test at the bench.
- TLJ-4 · What a result must say per field. Each field has one of three states, and the report gives the value read and where it came from.
  - chip: matches / differs / unknown. Source esptool step 2. Compared with the record's `chip` (E `boards/firebeetle2-esp32s3.json:5`).
  - flash size: matches / differs / unknown. The test that matters is "flash ≥ image" (the image is 4 MiB, E `scripts/flash_image.py:30-31`), not "flash = record". A 16 MB chip under a 4 MiB image is "differs, fine"; a 2 MB chip is "differs, cannot hold it" (E: IDF refuses a header larger than the detected flash, `Detected size(8192K) smaller than the size in the binary image header(16384K).Probe failed.`, Espressif FAQ via the docs server, 2026-10-13).
  - PSRAM and its mode: matches / differs / unknown. eFuse says "Embedded PSRAM 8MB" with a vendor (E esptool `esp32s3.py` `get_chip_features`); the mode (octal or quad) is not in that function (E: none printed). The mode is unknown from esptool. MicroPython can show the effect (heap size after boot, `esp32.idf_heap_info`, H).
  - USB mode: matches / differs / unknown, from VID:PID at step 0 and esptool's line if the pinned version prints one (— not read).
  - MAC: no "match" against the record, because the record holds no MAC. It is "known" and goes to Q6.
  - board maker, model and revision: always "unknown, cannot be read" (E TL-7). The result says so in words and never fills it by guessing. What fills it is the person, or a memory spark kept (Q6, TLJ-26).
  - what is on the board: "empty", "MicroPython with files X", "other firmware", or unknown. Source step 1 (and a marker file, Q8).
  · E/H as marked · supports only: the field list. The rule "unknown is not matches" is `docs/guide/agents.md` doctrine (E AGENTS.md).
- TLJ-5 · The side effects that matter for a check on a board somebody uses. (a) esptool's reset restarts a running gadget and its outputs pass through the bootloader's state. A motor input on a pin that the bootloader leaves floating may twitch (E `boards/firebeetle2-esp32s3.json` `pin_roles.console_uart` note: TX is "driven push-pull at boot, so anything that acts on a level ... twitches every time the board resets", GPIO43 and 44). (b) `mpremote exec` leaves main.py stopped, which for a gadget in the field means its loop is no longer running. (c) A board in its bootloader stays there after `--after no-reset` until it is reset. None of these is destructive. Each is something a check should say before it does it. · E for (a), H for (b) and (c) · supports only: what to warn about.

The firmware itself is not changed by spark ("facts, never behaviour"), but the facts it imports change.

### Q3. The firmware base, and PHYS-3 settled by a read

- TLJ-11 · PHYS-3 is settled by reading MicroPython's source and Espressif's, as far as reading goes. The chain of facts:
  1. v1.29.0's `ports/esp32/main.c`: if the partition table has neither a `vfs` nor an `ffat` partition, it finds the end of the last partition and "create[s] a "vfs" partition taking up all of that space", from that end "up to the end of flash", with `size = esp_flash_default_chip->size - offset` (E https://raw.githubusercontent.com/micropython/micropython/v1.29.0/ports/esp32/main.c, read 2026-10-13, via a summarising fetch that returned the block verbatim, lines 243-260 per the fetch).
  2. The kept v1.29.0 S3 `.bin` has no `vfs` entry; its table ends with `factory` at 0x10000 + 0x1f0000 = 0x200000 (measured by script in round 1, TL-14, PHYS-3). So the filesystem starts at 0x200000.
  3. In ESP-IDF, `esp_flash_default_chip->size` is "equal to ROM flash size (also equal to the size in binary image header), which means the available size that can be used". When the detected chip is bigger, the log says "Detected size(16384k) larger than the size in the binary image header(2048k). Using the size in the binary image header." (E https://github.com/espressif/esp-idf/blob/master/components/spi_flash/esp_flash_spi_init.c L586-612 and an example log from a 16 MB board, via the Espressif docs server, 2026-10-13; this is master, not the IDF that v1.29.0 uses — which is —).
  4. The image header's flash size is the build's: nibble 2 = 4 MB (measured round 1). esptool's default for `write-flash` is `--flash-size keep`, "the value in the bootloader .bin file header is kept instead of detecting the actual flash size and updating the header" (E https://docs.espressif.com/projects/esptool/en/latest/esp32/esptool/flash-modes.html, 2026-10-13).
  5. So the filesystem partition is 0x200000 to 0x400000: 4,194,304 − 2,097,152 = 2,097,152 B = 2 MiB = 512 blocks of 4096 B (calculated), which is the size `flash_image.py` writes (E `scripts/flash_image.py:31,40-41`: `block_count = (FLASH_SIZE - FILESYSTEM_OFFSET) // BLOCK_SIZE`).
  Result: with the image written as deploy does it (no `--flash-size` argument, E `scripts/deploy.py:132`), a 16 MB chip should boot with a 2 MiB filesystem that matches the image's littlefs, and 12 MiB of flash stay unused (calculated, round 1). · E for the five steps, H for "should boot" · supports only: master-branch IDF behaviour read on 2026-10-13 and the kept v1.29.0 table. This is a read that settles the arithmetic and does not prove the boot.
- TLJ-12 · What the one read does not settle. (a) Which IDF version builds v1.29.0: — (not read), so step 3 rests on master. (b) Whether the app and the bootloader read the same header (H, yes). (c) The failure path if a user passes `--flash-size detect` or a tool rewrites the header to 16 MB: then `size` becomes 16 MiB, the filesystem partition would be 0x200000 to 0x1000000 = 14 MiB = 3584 blocks (calculated), and a littlefs written for 512 blocks no longer matches the partition. That mount's outcome (refuse and reformat, or accept) is H from littlefs memory (round 1) and is not settled by this read. So the guard is: deploy must not pass a flash-size argument, or must test it. (d) The real behaviour on the board: bench, `os.statvfs('/')`. The expected value is a block count of 512 at 4096 B (calculated), 2 MiB. · E/H as marked · supports only: what remains.
- TLJ-13 · The base for a matching board. micropython.org offers, for the S3, a Standard file `ESP32_GENERIC_S3-20260824-v1.29.0.bin` and a `SPIRAM_OCT` file `ESP32_GENERIC_S3-SPIRAM_OCT-20260824-v1.29.0.bin`, both v1.29.0 dated 2026-08-24 (E https://micropython.org/download/ESP32_GENERIC_S3/, 2026-10-13, round 1). The tools list holds the Standard one, with URL and sha256 `1dd9dcd2…e300` (E `data/tools.json` `micropython-esp32s3`). A "download the matching base" step has the same shape as `/spark:setup add micropython-esp32s3` (E `data/tools.json` `install.download`). A second entry per (port, variant) would need: the URL, the sha256 and the printed version and date. The sha256 of the OCT file is — (not fetched; downloading is not allowed in this task). The rule in AGENTS.md: "Never commit a vendor file, because installing spark copies the whole repository. ... Cite a source by its URL, printed version, page and sha256". So the file is downloaded into the person's store, not into the repository, and the entry cites its URL and sha256 (E AGENTS.md). The sha256 of a file nobody has fetched can be pinned only after a first download that the person approves, or from a published digest if one exists (— for micropython.org; GitHub's release digests are used for wokwi-cli, E `data/tools.json` comment on wokwi-cli). · E · as pointed · supports only: the shape.
- TLJ-14 · "The firmware base" can also mean what was on the board before. spark cannot download that: the vendor's original image is not named by any record I read (— DFRobot publishes none that I read). The only way to keep it is a read-back with `esptool read-flash` (Q1 step 3), which costs the minutes in TLJ-2 and produces a file that can hold Wi-Fi credentials and the person's data. - TLJ-15 · What the simulation proves when the board's base differs from the simulated one. The simulated image is the Standard build plus `firmware/` in a 4 MiB image on Wokwi's S3 stand-in (E TL-16/PHYS-6). The two are not the same word and the difference is unexplained, —), the real USB enumeration, or PSRAM-dependent memory. Because the interpreter is inside the image, a different base is a different image, a different sha256, and under decision 1 (E `docs/archive/2026-10-12-p192-deploy-plan.md`) it needs its own passed run. A check can compare the board's `sys.implementation.version` and the build string `v1.29.0 on 2026-08-24` (E: the kept `.bin` carries "MicroPython v1.29.0 on 2026-08-24" by `strings`) with the image's, and say matches / differs / unknown. · E/H as marked · supports only: what the pass covers.

### Q5. The cheapest order of build steps (the walking skeleton first)

- TLJ-18 · One order, each step safe and working end to end, what each needs from the bench. Costs are in effort sizes already used on the board (S, M) and are Claude's estimates (H).
  1. Skeleton, the smallest deploy that obeys D4. `deploy.py` requires `--port`, prints what it will erase and the board it read (chip, flash, MAC) from one `flash-id`/`chip-id` call, compares chip and flash ≥ image, and asks the yes, bound to the port and MAC, before the erase. An ignore flag exists and is loud. Touches: `scripts/deploy.py` (and a small probe class in a library module, per "One core"). Needs from the bench: esptool 5.5.0's real lines, one board, one cable. Size S to M.
  2. The bench run itself (P215): flash and watch `ready`, with the read-only commands first, kept as fixtures. Needs the PO's board and about an hour.
  3. Memory of boards: a store record keyed by MAC with the board id the person confirmed (Q6). Touches the store/drawer (— `scripts/drawer.py` not read). Needs two readings of the same board.
  4. What is on the board: `mpremote` read of the REPL state, files and the marker (Q8). Needs a board with something on it (the board after step 2 qualifies).

### Q6. Two almost identical boards at once (D5)

- TLJ-19 · What tells two boards apart, with the evidence for each:
  - the MAC. Unique per chip, in eFuse. esptool reads it (`read-mac`, E TL-3). MicroPython reads it as `machine.unique_id()` (H, API from memory; the MicroPython page for `esp32` read here does not list it). It is a chip fact, not a board fact.
  - the USB serial number. For the S3's USB-Serial/JTAG in the ROM, "the Serial is set to the device MAC address", VID 0x303a, PID 0x1001 (E https://docs.espressif.com/projects/esp-iot-solution/en/latest/usb/usb_overview/usb_device_const_COM.html, 2026-10-13). So the host's port list shows the MAC before any byte is sent to the board. For an S3 running firmware with TinyUSB, the serial is whatever that firmware sets: Arduino-esp32 sets it from the MAC as `aa:bb:...` text (E arduino-esp32 `esp32-hal-tinyusb.c`, Espressif docs server), an ESP-IDF example uses the constant "123456" (E esp-dev-kits `usb_descriptors.c`). So the rule "serial = MAC" is true for the ROM and for MicroPython only if MicroPython's console is on the USB-Serial/JTAG (H, TL/PHYS-1). And it is not guaranteed after the person flashes other firmware.
  - the port path (`/dev/cu.usbmodemNNN`). It changes after the flash (E `commands/build.md:277`) and with the USB socket (H). It tells which socket, not which board.
  - `mpremote connect id:<serial>` selects by USB serial number (E mpremote docs, 2026-10-13). So spark can name a board by serial across a re-enumeration.
  - esptool takes a port path. It has no option I know of that selects by serial or checks an expected MAC (H, not read for 5.5.0). So spark has to resolve the serial to the current path and read the MAC again over that path before it writes. The window between the two calls is small and not zero.
  - the board's maker, model, revision: not readable (E TL-7).
  · E/H as marked · supports only: the list of discriminators.
- TLJ-20 · What spark could keep about each board it flashed. A record per MAC in the person's store, not in the repository: the MAC, the board id the person confirmed, the project, the image sha256 and the date flashed, and a name the person gave ("the car", "the remote"). The case exists in the PO's own work: the RC car has two circuits (E `council/po-assistant.md` PO-28, #205). Where it would live (the drawer holds what a person owns, E skill list entry for spark:drawer; whether it can hold a MAC is — , `scripts/drawer.py` not read) is a question. What it gives the check: "this port's MAC is the board you called 'the remote' last time, and its project is the remote's" — a memory, an H-level claim, kept by spark. It can be stale (a board swapped, firmware overwritten by another tool). So it feeds the report as "remembered", never as "read". · E for the RC-car case, H for the rest · supports only: the idea.
- TLJ-21 · What a safe check does when it cannot tell two boards apart. Cases: (a) two ports with the same VID:PID and different serials (the common case for two S3 boards): the check can tell them apart by serial, lists both with the MAC and any remembered name, and requires the person to pick; (b) two ports with equal or missing serials (OTG/TinyUSB firmware with a constant serial, bridge-chip boards): it cannot tell them apart by any read; it stops, and says to unplug one, because esptool "tries each port" if none is named (E `scripts/deploy.py:166`); (c) a port that vanishes and reappears between the check and the write (the board resets on its own, or the cable is knocked): the MAC read must be repeated over the path used for the write, and if the second read gives another MAC, stop. (d) two boards of the same model with different flash sizes (N16R8 and N4): flash size separates them, and the check still reports both. In every case the yes names the MAC, not the path. · H · Claude's reading of the discriminators · supports only: stop-and-ask as the default when a read cannot separate them.

### Q7. OTA

- TLJ-22 · What exists in MicroPython and what an OTA update needs from it.
  - Partitions: the shipped table has `nvs`, `phy_init` and `factory` only (measured by script from the kept `.bin`, round 1), so there is no second app slot and no `otadata`. OTA needs a table with two app slots and `otadata`. That changes the layout `flash_image.py` and the filesystem start assume (E `scripts/flash_image.py:30-31`). The N16R8 has space for it (12 MiB unused, calculated, TLJ-11). Whether a build with such a table is on micropython.org for the S3 is — (not read; the page lists Standard, SPIRAM_OCT and an obsolete FLASH_4M, E).
  - API: `esp32.Partition` has `find()`, `info()`, `set_boot()`, `get_next_update()` ("typical usage is `Partition(Partition.RUNNING).get_next_update()`"), `mark_app_valid_cancel_rollback()` ("required on the first boot of a new partition to avoid an automatic rollback at the next boot" when rollback is enabled), `Partition.BOOT` and `RUNNING`. A warning: do not enter deep sleep after changing the OTA boot partition without a hard reset or power cycle (E https://docs.micropython.org/en/latest/library/esp32.html, read 2026-10-13).
  - Files over the network: WebREPL, "an experimental feature", enabled with `import webrepl_setup`, started with `webrepl.start(password=...)`, and it "listens on all active interfaces (STA or AP)" (E https://docs.micropython.org/en/latest/esp32/quickref.html, 2026-10-13). `mip` installs packages over the network (E mpremote command list). `mpremote connect rfc2217://host:port` is serial over TCP and needs a bridge (E mpremote docs). The quickref says nothing about OTA (E: "No section on OTA updates appears").
  · E · as pointed · supports only: what is documented. A MicroPython-level OTA of the interpreter needs a different build. A file update over Wi-Fi needs code on the board, and that code is firmware.
- TLJ-23 · What it needs for Arduino and PlatformIO. Arduino-esp32 ships OTA helpers (`ArduinoOTA`, `Update`, `HTTPUpdate`) and partition schemes with two app slots (H, model knowledge, not read). PlatformIO has an `espota` upload protocol (H, not read). ESP-IDF has `esp_https_ota`, `otadata` and rollback (H; the MicroPython API above mirrors it). I read none of these this session. Each needs: a partition table with two app slots, the app-only binary (not the whole-flash image), a transport, and an authenticity rule. · H · model knowledge · supports only: a list to confirm in the P221 spike.
- TLJ-24 · How "only the image that passed goes on the board" can hold over the air. Today the passed artefact is the whole-flash image: the log header names its sha256 (E `scripts/run_scenario.py:49-50,180-200`). An OTA delivers an app binary and perhaps files, not the whole flash. Three consequences. (1) The sim has to test the thing that OTA delivers, or the pass names a different object than the one sent. Wokwi takes an app-only `.bin` and adds its own bootloader and a default table (E https://docs.wokwi.com/vscode/project-config, 2026-10-13, TL-16), so for Arduino/PlatformIO the app binary can be the passed artefact. For the MicroPython image it cannot, because the interpreter and files are in one flash image. (2) The log would have to name the OTA artefact's sha256 as a second line, with one writer and one reader (as for the image). (3) The check on the board before `set_boot` — compare the received bytes' sha256 with the expected one — is firmware behaviour. Spark can export the expected sha256 as a fact (a file or a constant), and the firmware that checks it is written in the conversation, not by spark (E AGENTS.md). Authenticity (a hash on an unauthenticated channel only detects corruption) needs signing, which is a further piece: — . · E for the log mechanism and the Wokwi fact, H for the rest · supports only: the three consequences.
- TLJ-25 · Safety risks of OTA, each with its mitigation named, not chosen. (a) A failed update: the new slot is written while the old slot still boots, so a power cut mid-write leaves the old firmware (H, ESP-IDF design; MicroPython's page says `set_boot` switches the slot). (b) Rollback: without `mark_app_valid_cancel_rollback()` a build with rollback enabled reverts at the next boot (E esp32 docs); a build without it could bootloop on a bad image (H). (c) Credentials: the Wi-Fi password lives on the board (a `/config.json` in the image is possible, E `scripts/flash_image.py:6`); WebREPL has one password on all interfaces (E quickref); an HTTP update server with no TLS shows the firmware to the network (H). (d) Targeting: an update reaching the wrong device (two near-identical boards, Q6), so the board's MAC must be part of what the update names. (e) Recovery: an image that kills Wi-Fi or USB needs BOOT and RESET by hand. (f) Cost to this epic: it needs a changed partition table, a transport and a server, none of which spark has; the PO put OTA to the decider as an open question (E brief). · E/H as marked · supports only: the risk list.

### Q8. A protocol between spark and the board's firmware

- TLJ-26 · What exists today. (1) The `ready` contract: the firmware prints a line containing `ready` once its setup is done, and nothing else containing that word before (E `scripts/run_scenario.py:7`, `commands/build.md`). The simulation waits for it (E `run_scenario.py:40`). On the board it is read by a person at a REPL (E `scripts/deploy.py:187`). (2) The run log header: date, verdict, `image sha256:` (E `scripts/run_scenario.py:49-50,180-200`). It lives on the host in `sim/runs/`. (3) `firmware/pins.py` is in the image and its first lines are a fact marker: `# The pin map: written by spark's assign_pins.py from <requirements file>` and `# for the <board name>. Regenerate it; do not edit it.` (E `scripts/assign_pins.py:392-419`, `PIN_MODULE_HEADER`). So the board already carries its board's name and the requirements file's name in a file, readable by `mpremote exec "print(open('pins.py').readline())"` (H for the exact REPL line; E for what the file holds). - TLJ-27 · What a small contract could carry, and what it costs. Candidate: a data file spark writes into the image's filesystem next to the project's files (the same way `/config.json` is added, E `scripts/flash_image.py:6,56`), holding facts only: a schema number, the project name, the board id, the chip, the pin map's sha256, the interpreter's build string, the per-file sha256 of the firmware files, spark's version, the date. The check reads it back over the REPL and says matches, differs or unknown (absent). No firmware has to read it, so it adds no behaviour on the board. Constraints found by reading:
  - the file cannot hold the sha256 of the image that contains it (the hash would change as the file is written). It can hold the interpreter's sha256 and the per-file hashes, which are what the image is made from. The run log then names the same facts.
  - a per-file hash list is also what TL-13 (round 1) needed for an update path under decision 1, and the check can recompute a file's sha256 on the board (`hashlib` in the ESP32 builds: H) to catch a file that someone edited after the flash. Without that recomputation the marker is a claim, as stale as the last flash.
  - the MAC cannot be in the file: it is not known when the image is made. The "which board is which" memory (TLJ-20) therefore stays on the host.
  - for Arduino/PlatformIO there is no REPL and often no filesystem in the image: the same facts could be a generated header (like `pins.h`, TL-17) and a constant the firmware may print. Printing it is a firmware choice, written in the conversation.
  - the USB-Serial/JTAG control lines reset the chip when a terminal opens the port (H), so a protocol that depends on a serial request/response at boot is fragile. Reading a file over the REPL after boot is not.
  · E for `/config.json` as a precedent and the log mechanism, H for the rest · supports only: a shape. It stays inside "Spark exports facts, never behaviour" because every field is a fact derived from a record spark holds (E AGENTS.md); any printing or checking in the firmware is not spark's.
- TLJ-28 · What the marker would give each journey. The check (Q1) learns "this board holds project X, image facts Y" without a Wokwi run; the better-match offer (Q2) learns what is already on the board; the update path (round 1 TL-13) gets its per-file proof; OTA (TLJ-24) gets an expected hash; two boards (Q6) gain nothing from the file itself, because both carry the same file if flashed from the same project. A marker lets a check say "this board was flashed by spark from project X" and does not say "this is the board the project is for" — that remains the person's yes and the host-side memory. · H · Claude's reading · supports only: what the contract settles and what it does not.

- TLJ-37 · The guards for live tries.
  - A pin the wiring drives. A write to a pad that the wiring ties to a driver, a supply or another output is contention. spark knows each signal's GPIO (E `pins.py` content, `scripts/assign_pins.py:392-419`), which GPIOs have roles that need care (E `pin_roles`: strapping 0 and 3, console 43 and 44, USB pins absent from `pins`, onboard LED 21, onboard button 47), and the part needs. It does not know a signal's direction in `pins.py` (TLJ-11 in round 1). So a guard that allows an output write only to a signal that a part's need marks as an output requires that direction to be exported (a fact with an origin: the part record's need). Without it the safe default is read-only: input reads, ADC reads and I2C scans, with writes asked of the person. An I2C scan is not read-only for the bus (it sends addresses), so it sits between the two.
  - A loop that holds the REPL. `mpremote` interrupts a running program (E docs), which works when the loop does not swallow `KeyboardInterrupt` and does not sit in `deepsleep` (native USB then disappears, H). Fallbacks, from cheapest: a second interrupt; `soft-reset`; a hard reset by esptool (`--after hard_reset` ends every esptool call, E); the person's RESET button. The `bootloader` subcommand puts the board into its bootloader (E docs, port-specific). A timeout on every call stops Claude waiting forever.
  - A try that writes flash. The tools that write are `fs cp`, `fs rm`, `fs mkdir`, `mip install`, `rtc --set`, `romfs deploy` and any Python in `exec` that opens a file for writing, calls `os.remove`, `mkfs` or `esp32.Partition.writeblocks`. A text filter on free-form `exec` code cannot be complete (H). A narrow set of verbs (read a pin, scan the bus, call a named function, read a file) can be, and free-form `exec` stays behind a yes. Mount and run leave the flash alone and are the way to try code without writing (above).
  - One owner of the port at a time. A human's terminal on the same port and Claude's commands contend (H for serial; WebREPL allows one connection at all, E README).
  - State the board is left in is reported after each try: main.py stopped or not, pads configured, and whether a reset is needed to get the gadget back.
  · E/H as marked · supports only: guards named. They decide nothing.
- TLJ-38 · What the bench must prove for live tries, each a short run on the PO's board: `exec` with a read of a pin returns, and `soft-reset` brings main.py back; a loop that catches `KeyboardInterrupt` is or is not interruptible (write one on purpose in a scratch folder, not in the project); `mount` plus `exec` imports a file from the host (the H above); a pin written as an output on an unwired pad stays driven or released across `soft-reset`; WebREPL (if the PO wants it) accepts `webrepl_cli.py put` and shows the port number. · H · Claude's cut · supports only: the list.
