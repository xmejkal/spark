## 1. Findings (WF-n)

### Which browser flashers exist

- WF-1 · Web Serial is the base for all of them. It lets a web page talk to a serial device; it needs a secure context (HTTPS); the person must grant a port by a click (`requestPort()`), so a page cannot open a port on its own; MDN calls its availability "limited", not baseline across browsers. · E https://developer.mozilla.org/en-US/docs/Web/API/Web_Serial_API, read 2026-10-13 · supports only: a page cannot start a flash without the person's click and port choice. That matches D4 for the port, but the choice is the person's in the browser's own dialog, not spark's.
- WF-2 · esptool-js: Espressif's JavaScript port of esptool; Apache-2.0; maintained by Espressif (Copyright 2023); 542 stars, 182 forks, 247 commits on main when read; a live demo at espressif.github.io/esptool-js. It can flash, erase flash (all or regions) and read flash; it cannot make an image from an ELF and has no espefuse/espsecure. APIs: `writeFlash()` (file array, flash mode, frequency, size, compression, progress callbacks) and `eraseFlash()`. Works in Chrome and Edge 89 or later and Chrome on Android 61 or later; a polyfill widens it. It is a library, not a ready page. · E https://github.com/espressif/esptool-js, read 2026-10-13 · supports only: the engine under the others; the one to embed if spark ever ships its own page.
- WF-3 · ESP Web Tools (maker: ESPHome / Nabu Casa, per the repository path esphome/esp-web-tools; licence Apache-2.0, per the repository page read): an `<esp-web-install-button>` element that points to a `manifest.json`. The manifest lists builds per chip family (ESP8266 and ESP32 variants), each with parts (file path and flash offset). The tool detects the connected chip and selects the build for that family; an optional `serialType` separates native USB CDC from a USB-UART bridge. For a new install it offers an "erase data" choice (the manifest field `new_install_prompt_erase`). After the flash, if the firmware supports Improv Wi-Fi, the person sets Wi-Fi in the browser. Needs HTTPS. Its page says it runs in Firefox, Chrome and Edge but not on iOS. · E https://github.com/esphome/esp-web-tools and https://esphome.github.io/esp-web-tools/, read 2026-10-13 · supports only: the model for "manifest keyed by chip, installed from a page". The text read did not say what the tool reads beyond the chip family (flash size, MAC, PSRAM) — unknown, and whether the manifest can say a build needs PSRAM — unknown. The Firefox claim conflicts with MDN's "limited availability" (WF-1) and with the Espressif/other snippets that name Chrome and Edge only; one search snippet says "Firefox 151 or later", which I did not verify. Treat Firefox as unknown.
- WF-4 · Improv Wi-Fi: an open standard where a device on serial (or Bluetooth) accepts Wi-Fi credentials from the host; ESP Web Tools shows the form after the flash when the firmware speaks Improv. It needs support in the firmware. · E same ESP Web Tools page, read 2026-10-13; the Improv specification itself — not read · supports only: Wi-Fi setup after a flash needs firmware cooperation; the MicroPython image spark builds has none (H, from its contents in round 2 POJ-15: no identity or Improv code found), so Improv is a firmware behaviour the conversation would have to write.
- WF-5 · Adafruit WebSerial ESPTool: a web tool to install firmware on ESP devices through the ROM bootloader; originally by Melissa LeBlanc-Williams, ported to TypeScript and maintained by Nabu Casa from March 2022, then back with Adafruit; since December 2024 it uses Espressif's esptool-js as its backend. Hosted at adafruit.github.io/Adafruit_WebSerial_ESPTool. A fork, tasmota-webserial-esptool, exists. Licence: not read (H: open source, MIT, unverified). · E web search "Espressif ESP Launchpad web flasher Adafruit WebSerial ESPTool licence browser Chrome Edge", result github.com/Jason2866/WebSerial_ESPTool and the git.morozoff.pro mirror of Adafruit's repository, read 2026-10-13, snippets · supports only: the maker-facing "pick a file and flash" page; a hosted tool the person points at a file.
- WF-6 · ESP Launchpad: Espressif's web tool for flashing from a browser with no local environment. Two modes: Quick Start (plug in, connect, choose a built-in firmware such as RainMaker or Matter examples by chip, flash) and DIY mode (the person's own images from disk, one file or several at given offsets). It also lets a maker publish firmware for others to try. Licence and repository: not read (the search returned Espressif documentation pages, not the repository). · E same family of results: docs.espressif.com/projects/esp-techpedia (Selecting the Suitable Flashing Platform), read 2026-10-13, snippet · supports only: DIY mode with several files at offsets is the shape of spark's image; there is no reason to think it understands MicroPython's layout.
- WF-7 · MicroPython and Thonny: Thonny is a desktop installer (round 2 POJ-4), not a web page. For MicroPython in the browser, ViperIDE (author Volodymyr Shymanskyy; MIT; Free and Open Source per the search snippet) connects to a board over USB/Serial, WebREPL over the internet or the local network, Bluetooth LE or a WebRTC bridge, with a file manager, editor and REPL. Its firmware advice: a download page with firmware for most boards, and drag-and-drop for .uf2 boards. I found no evidence that ViperIDE flashes an ESP32 itself (an ESP32 needs esptool-style flashing): — unknown. micropython.org's own download page lists builds (round 2 POJ-6) and, in the snippets read, no web flasher — unknown. · E web search "ViperIDE MicroPython browser IDE Web Serial install MicroPython firmware licence", results incl. tomshardware.com and alternativeto.net, read 2026-10-13 (snippets) · supports only: ViperIDE is a live-REPL tool (D7), not the flashing tool; it overlaps D7 more than D4.

### What it does for the people, and for Claude

- WF-8 · For a person with no Python and no esptool: a Chromium browser, a USB cable and a click replaces `pip install esptool`, the port name hunt and the terminal. This is the baseline the PO's "I think there was one" points to, and the reason makers use them. The person still presses BOOT and RESET if the board needs it; native-USB S3 boards may put themselves in download mode (round 2 PHYS-2, E from the tech lead). · E for the mechanism (WF-1 to WF-3); H for the maker benefit (Claude, from the install steps) · supports only: a beginner value spark does not offer today, given that `/spark:setup` installs esptool by pip (round 1 PO-2).
- WF-9 · For Claude: little. A browser page needs a click to grant a port (WF-1) and a human watching the dialog; Claude can write a manifest and tell the person which button to press, or drive a browser through the Chrome tools, but an agent clicking through the port dialog is what D4 means by "never without the person's yes" turned inside out: the browser's own permission prompt replaces spark's yes, and spark does not see the result. There is no JSON answer to read back (the page's own log is on screen, not in a file). · H (Claude, from WF-1; the Chrome extension route was not tested) · supports only: the web flasher serves rung 0 for a person, not an agent. For Claude it adds nothing over `deploy.py`.

### How it could be integrated: three shapes (proposals)

- WF-10 · Shape A, a hosted page that the person opens (ESP Web Tools or Adafruit/Espressif pages) with the spark image downloaded from the project folder. Under D4: the page asks the chip family only, erases if the person ticks or accepts (the default prompt for a new install, WF-3), and knows nothing of spark's passed run, the board record or the sha256. The person could pick any file. spark's gate (flash only an image a passed run names) is bypassed completely. Under D6: nothing is known to the page, so it can never be silent. Under D8: it bypasses the core. · H, from WF-2, WF-3 and scripts/deploy.py (untested, plan) · supports only: Shape A fails D4 and D8 as written; its only use is a manual escape hatch for a person without Python.
- WF-11 · Shape B, a local page that spark's core generates: the core runs its checks (a passed run names the image; the board record agrees where it can), then writes the `manifest.json` and copies the image into a local folder, and a small local web server (loopback, `http://localhost` counts as a secure context in browsers; H, model knowledge, not read here) serves the page with the ESP Web Tools button or an esptool-js page. The manifest lists only the image the core vetted, with the chip family from the board record. The person clicks, picks the port in the browser's dialog and flashes. Under D4: the core decides what can be flashed (the manifest and the image exist only after its checks), but the board check (read-only identity: chip, flash size, MAC) would have to be done in the page by esptool-js, whose results the core must read back; ESP Web Tools by itself checks the chip family only (WF-3). Under D8: the core stays the decider, the web page is a thin interface; the cost is a second interface to keep, a local server, and the page's result channel (a log the core can read: the page would post its outcome to the local server). Under D6: for a known board the page could be started and clicked silently only if the person already granted the port (`getPorts()`, WF-1), which is a browser setting spark does not control; the click and port grant remain. · H, built from WF-1 to WF-3 and the coordinator's D8 sketch · supports only: the one shape that keeps the gate; still a proposal, not a design, and its cost has not been estimated.
- WF-12 · Shape C, esptool-js embedded in a page spark ships, with the read-only identity steps written in JavaScript against spark's board record (JSON). This runs the same checks as `deploy.py` in a second language, the repeat of logic that AGENTS.md says an interface must not hold ("An agent prompt never repeats its logic"; "One core, many interfaces"). Unless the page only asks the core's local server for its verdict (Shape B), it forks the logic. · E AGENTS.md "Principles for changing spark"; H for the reading · supports only: C only as part of B, with the core as the one place that decides.

### Risks of a browser flasher

- WF-13 · Chromium only (Chrome, Edge, Opera; Android Chrome), with Firefox and Safari unknown or no (WF-1, WF-3 conflict, no verification); iOS excluded (WF-3). The PO works on a Mac with Claude Code, so Chrome is likely present (the Claude in Chrome tools exist in this session, E tool list), but a stranger's browser is not known. · E MDN and the ESP Web Tools page; H for the stranger · supports only: a Chromium dependency is a new support surface for "a user installs nothing heavy".
- WF-14 · A hosted page versus a local one: a hosted page (Shape A) runs code from someone else's server at the moment of the flash and is out of spark's hands (updates, outage, change of behaviour); a local page (Shape B) is spark's code but needs a server and a secure-context rule. The Web Serial specification requires a secure context (WF-1). Spark's "free, few and local" rule favours local. · E WF-1; H for the rest · supports only: if a web flasher is ever offered, local.
- WF-15 · The image that passed versus what the page flashes: a page flashes whatever file or manifest it is given; nothing ties it to the run log's sha256 (round 1 PO-1, scripts/deploy.py untested). The offsets must also match: `deploy.py` writes one file at 0x0 (scripts/deploy.py:33, IMAGE_OFFSET); a manifest for that is a single part at offset 0. ESP Web Tools' manifest names offsets, so it can express that (WF-3); whether it would write at 0 without its own bootloader assumptions was not tested — unknown. · E scripts/deploy.py:33; WF-3 · supports only: the image-name gate must be in the core, not the page.
- WF-16 · The erase: ESP Web Tools' erase is a prompt for a new install (WF-3) and esptool-js `eraseFlash()` is a function (WF-2); neither is tied to spark's yes or board check unless the core wraps them. spark's own erase today also has no code prompt (round 1 PO-23, USER-2). · E WF-2, WF-3, round 1 PO-23 · supports only: a web flasher does not make the erase safer by itself; it moves the decision to the page.
- WF-17 · The port dialog is the browser's, not spark's: with two nearly identical boards (D5, round 2 POJ-9) the dialog lists ports by name and USB description, not by MAC; the person chooses, and spark does not see which. The page could read the MAC after connecting (esptool-js reads chip info; H, not verified for the MAC) and refuse; again that needs the core's stored identity. · E WF-1; H for the rest · supports only: the two-board case is the same as in `deploy.py`, no easier in a browser.
- WF-18 · Secrets and trust: a hosted page runs third-party JavaScript with serial access to the board; a local page runs spark's. Neither stores credentials unless Improv is used (WF-4), where the Wi-Fi password passes through the page. · H · supports only: spark should not offer Improv-style Wi-Fi entry in a page without a decision from the PO.
- WF-19 · Where it overlaps what spark has: `deploy.py` already does the same flash in Python for the same board (round 1 PO-1); `mpremote`/belay already give a script the live REPL (round 2 D7). The web flasher's only additions are no-Python installation and a GUI for the person. · E round 1 PO-1; round 2 POJ-35, POJ-37 · supports only: the value is for a person without Python; for spark's current user (the PO) it replaces nothing he lacks.

### Opinion (the PO assistant's, marked as mine)

- WF-20 · OPINION (PO assistant, H): a web flasher is useful for one journey rung only, the first-time install by a person who has no Python and no esptool (the stranger of scrum/VISION.md, "the hobbyist"; round 1 PO-18 says that persona is a hypothesis with no outsider yet). It is not useful for the known-board path K (round 2 POJ-33), because the port grant and the click cannot be silent, and not useful for Claude (WF-9). For the PO's own Mac with `esptool` installed by `/spark:setup`, it adds nothing today. If the PO wants it, Shape B (core generates manifest and image after its checks, local server, thin page) is the only shape I found that keeps D4 and D8, and it should come after the bench shows the plain `deploy.py` works (P215), and after the identity check (round 2 slice 0). The cheapest first step is a read-only spike, not code: in a Chromium browser, open the Espressif esptool-js demo on the PO's board and write down what it reads (chip, flash size, MAC, PSRAM) with the board connected, and whether it can flash a spark image at 0x0. Pass line, set before the run: it shows the MAC and flash size and flashes the image to `ready`, without anything installed. That one run also answers two things I could not read: what the chip detection returns, and whether the S3's native USB works in the browser. · H · supports only: it is mine.

## 2. What I could not check, and why

- Licences of Adafruit's WebSerial ESPTool, ESP Launchpad, ESP Web Tools beyond the repository navigation text, and the Improv specification: not read at source.
- What ESP Web Tools and esptool-js read from the chip beyond the family (flash size, MAC, PSRAM, revision), and whether a manifest can carry flash or PSRAM conditions: the pages read did not say.
- Which browsers support Web Serial now, including Firefox: MDN says "limited", two sources conflict, and the compatibility table was not opened.
- Whether `http://localhost` is a secure context for Web Serial: model knowledge, not read here.
- Whether a Chrome-driven agent (the Claude in Chrome tools) can pass the Web Serial port dialog: not tested, and not tried without the PO's yes (nothing was run against a board).
- Whether ESP Web Tools writes one image at offset 0 (a whole-flash image) correctly on an S3, and whether esptool-js works with the S3's native USB: needs the board.
- Whether the MicroPython project or ViperIDE offers an ESP32 flasher in the browser: the snippets did not show one.
- Estimated cost of Shape B (server, page, result channel): not made.
- D8's wording in brief.md: it was not there when I read the brief (lines 71 to 73 hold D5 to D7); I used the coordinator's message.
