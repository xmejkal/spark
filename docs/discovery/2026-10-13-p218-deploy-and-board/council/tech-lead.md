### Q2. P222: the REPL and a live connection

- TL-9 · What mpremote does, from its docs (latest, read 2026-10-13):
  - `connect` takes `list`, `auto`, `id:<serial>`, `port:<path>` or `rfc2217://`; `auto` "will only detect USB serial ports, i.e. a serial port that has an associated USB VID/PID";
  - `exec` follows the output until the expression ends, `--no-follow` returns at once;
  - `run` "will execute the file directly from RAM on the device without copying it to the filesystem" and is "executed in raw REPL after a soft reset, so the device's own `main.py` is not run beforehand";
  - an action command "will interrupt a running program, but the Python heap is left alone";
  - `resume` "skips that soft-reset for a single invocation";
  - `mount` mounts a local directory as `/remote` using the serial line as a side channel, and by default errors on a path outside the mounted directory;
  - `fs cp` uses a leading `:` for a remote path;
  - `repl --capture <file>` saves the session;
  - `bootloader` is port- and board-specific;
  - `romfs`, `rtc`, `mip` exist.
  · E · https://docs.micropython.org/en/latest/reference/mpremote.html, read 2026-10-13 (page text via a summarising fetch, verbatim quotes as returned) · supports only: that page version. The installed mpremote is 1.29.0 (E, `mpremote version`), the pin.
- TL-10 · Raw REPL and raw-paste, from MicroPython's REPL doc: raw mode is entered with Ctrl-A, code is sent followed by Ctrl-D, and the device answers "OK". Raw-paste is requested with `\x05A\x01`, answered `R\x01` when supported, and uses a window-size flow control with `\x01` (more window) and `\x04` (end). Ctrl-D from the REPL is a soft reset that "tries not to reset the method by which you're connected". The page said nothing about `boot.py`, `main.py` or loops. · E · https://docs.micropython.org/en/latest/reference/repl.html, read 2026-10-13 · supports only: the protocol. ## PHYS: electronics-firmware:physics (the PO's board: FireBeetle 2 ESP32-S3 N16R8, DFR0975)

- PHYS-1 · Native USB and a boot-time `ready`. The USB-C goes to the chip's own USB (DFRobot's wiki lists "USB: USB 2.0 OTG full-speed", E https://wiki.dfrobot.com/SKU_DFR0975_FireBeetle_2_Board_ESP32_S3, read 2026-10-13). No USB-UART bridge is named. Espressif's doc says the USB Serial/JTAG controller's CDC port is connected "directly to a host/PC" and "does not require an external USB-UART bridge chip", on GPIO19 (D-) and GPIO20 (D+). MicroPython's console on this board goes over which of Serial/JTAG or OTG-CDC is · H (the kept .bin contains the string "USB_SERIAL_JTAG", E by `strings`, but that string is also in ESP-IDF generics, so it does not prove the console). Consequence if the host port only exists once USB enumerates: a `ready` printed in the first moments after a hard reset can be printed before the host has a port to read, and is lost. A soft reset (Ctrl-D, which `deploy.py`'s watch instruction uses: E `scripts/deploy.py:40-41,187`) keeps the USB connection, so the `ready` of a soft reset reaches the host (H from the REPL page's "tries not to reset the method by which you're connected", E TL-10, for the soft-reset half). That the S3's hard reset drops the port is · H · model knowledge, not read here. The deploy plan already leaves this to the bench (E `docs/2026-10-12-p192-deploy-plan.md` decision 6). Cheapest rung that settles it: at the bench, `mpremote connect <port> repl --capture out.txt`, press RESET, then Ctrl-D; read whether `ready` appears in each case; cost: 5 minutes, no meter. What that rung cannot show: behaviour with another host OS, a hub, or a power-only cable; and nothing about a board running from battery with no host. · supports only: the host Mac on the bench.
- PHYS-2 · BOOT and RESET. DFRobot's FAQ: "Press Boot, press RST and release both, then try burning again." (E, wiki above, read 2026-10-13). Espressif's guide says the USB Serial/JTAG controller "is able to put the ESP32-S3 into download mode automatically", so plain `esptool` on the right port may need no buttons (E https://docs.espressif.com/projects/esp-idf/en/latest/esp32s3/api-guides/usb-serial-jtag-console.html, via the Espressif docs server, 2026-10-13). The two differ in scope: DFRobot's is the fallback, Espressif's the normal route. `deploy.py`'s hint is the fallback form: hold BOOT, press RESET, release BOOT (E `scripts/deploy.py:38-39`), which is not the same sequence as DFRobot's ("press Boot, press RST, release both"). The result is the same download-mode entry in both: — (the order difference is unmeasured). BOOT is GPIO0, D9, a strapping pin (E `boards/firebeetle2-esp32s3.json` `pin_roles.strapping`). Errata: on S3 with chip date code before 2219 / module PW before PW-2022-06 the USB-OTG download function is unavailable (eFuse set), and USB-Serial-JTAG download is the workaround (E https://docs.espressif.com/projects/esp-chip-errata/en/latest/esp32s3/03-errata-description/esp32s3/usb-otg-download-func-bug.html, 2026-10-13). Whether the PO's board is such a batch is — (the chip's date code is printed on the module). Cheapest rung: run `esptool flash-id` with no buttons, then with BOOT/RESET, at the bench. Cannot show: reliability over many boards.
- PHYS-3 · Flash against image. Stated: N16R8 has 16 MB flash and 8 MB octal PSRAM (E `boards/firebeetle2-esp32s3.json:9`; DFRobot wiki, "Flash: 16MB", "PSRAM: 8MB", read 2026-10-13). The image is `FLASH_SIZE = 4 * 1024 * 1024` = 4,194,304 bytes (E `scripts/flash_image.py:30`). Calculated, python: 16 MiB = 16,777,216 B (taking "16 MB" as 16 MiB: stated unit is — in the sources); unused = 12,582,912 B = 12 MiB; the image is 25 % of the flash. The kept MicroPython .bin is 1,783,296 B (1.70 MiB, measured); its header names a 4 MB flash size (nibble 2 of byte 3, measured by script) and its partition table is `nvs` 0x9000/24 KiB, `phy_init` 0xf000/4 KiB, `factory` 0x10000/0x1f0000, ending at 0x200000, with no `vfs` entry (measured by script from the kept .bin). The littlefs the spark image writes begins at 0x200000 and spans 512 blocks of 4096 B = 2 MiB (E `scripts/flash_image.py:31,40-41`; calculated). esptool's `write-flash` "default is to keep the flash mode and size from the .bin image file" (E esptool docs, read 2026-10-13: page version latest, v5.5.0 not confirmed), so the chip keeps booting with a 4 MB header on 16 MB flash, which is H, not read. **Open and the highest-stakes physical question: where does MicroPython put its filesystem on a 16 MB chip, given the table has no `vfs` entry?** If it takes the space after `factory` up to the detected 16 MB, the superblock of the 2 MiB littlefs says 512 blocks while the device would say 3584 (calculated: (16 MiB − 2 MiB)/4096), and littlefs refuses a mount whose block count differs (H, littlefs source from memory, not read). MicroPython would then format the filesystem on first boot. `main.py` would be gone, and the board would show a bare REPL with no `ready`. `flash_image.py`'s own header names this symptom: "the simulated board boots to a bare REPL with no main.py" (E `scripts/flash_image.py:14-16`). Cheapest rung: a code read of `ports/esp32` in MicroPython v1.29.0 for how the vfs region is chosen (no board, costs no Wokwi minute; not done, search budget used), then the bench: after the flash, `mpremote fs ls` and `exec "import os; print(os.statvfs('/'))"`. What the read cannot show: the real flash size the firmware detects. What the bench cannot show: other flash sizes (the N4 SKU).

- PHYS-7 · Hardware revisions V1.1 and V1.2. DFRobot's wiki labels two Board Overview tabs: "Version V1.1 and earlier" and "Version V1.2 and later", and states "V1.1 and below: AXP313A" versus "V1.2 and above: three independent power supply circuits" (E wiki, read 2026-10-13). The record agrees: V1.1 and earlier has an AXP313A PMIC (DCDC1 1.5 A), 5.1 k pull-ups on SDA and SCL already present, and a user button that also drives the PMIC's PWRON (a long press can power the board down). V1.2 and later has a TPS62A02 (2 A) and "NONE anywhere on the board" for I2C pull-ups (E `boards/firebeetle2-esp32s3.json:298-318`, citing the V1.0 and V1.3 schematics). How to tell by eye, from the record: "A QFN marked AXP313A is V1.1 or earlier; a tiny SOT-563 next to two SOT-23-5 LDOs is V1.2 or later. The back silkscreen also carries the revision." (same file). Not readable by esptool or MicroPython (TL-7). So two rungs: (rung 1) look at the board and its back silkscreen, cost zero, and gives V1.1 or V1.2 directly: this is the card's own suggestion (#196). (Rung 2, only if the board cannot be inspected, an inference, H) set GPIO1 (SDA) as an input with the internal pull-down and read it with nothing connected to GPIO1/GPIO2. Calculated in python: with 3.3 V (stated), the 5.1 kΩ pull-up (stated, record) and 45 kΩ as the internal resistor's typical value (the record's `internal_pull_up_ohms`, datasheet-typ for the pull-up, which I assume equal for the pull-down: H), a V1.1 board's pin sits at 3.3 × 45/(45+5.1) = 2.96 V, 0.90 of VDD; with 30 kΩ it is 2.82 V and with 65 kΩ 3.06 V (sensitivity, my range, not a datasheet bound). The input threshold VIH = 0.75 VDD = 2.47 V is · H · datasheet not read this session. So a V1.1 board would read 1 and a V1.2 board 0. Rung 2 cannot show: a board with a part still on the breadboard's SDA, or a V1.1 whose pull-up has been modified. It is also not a proof of the PMIC.
- PHYS-8 · The B21 / bin #15 pointer. The card says "read the board's hardware revision, V1.1 or V1.2 (B21, bin #15)" (E #196 body). The bin repository is not in this repository, so B21's content is — (not read). Two documents disagree on what the revision change affects: the record says VCC "follows VSYS" (`power.vcc_is_not_tied_to_vsys`, E `boards/firebeetle2-esp32s3.json` ~362) and also says "with nothing on the rail it carries the USB 5 V OUT" (`:142`, E; same file). DFRobot's wiki says VCC "outputs USB voltage when powered by USB or battery voltage when powered by Li-ion" (E wiki read 2026-10-13). #73 (P139) quotes DFRobot's V1.0 and V1.3 schematics and the ETA6003 datasheet p.3: VSYS is 3.6 V minimum (default) and 4.5 V maximum at VIN = 5 V, so the pad is "0.5–1.4 V short of 5 V" (E #73 body, read 2026-10-13; the datasheet itself not re-read by me). 5.0 − 4.5 = 0.5 and 5.0 − 3.6 = 1.4, calculated from those two stated numbers. #73 says the deciding meter reading at "B14" is a reading of VCC with only USB plugged in. For deploy: the VCC pad does not affect flashing or the REPL. It matters to what an agent drives on a real board (a part fed from VCC gets 3.6–4.5 V, not 5 V, if #73 is right). Cheapest rung: the meter reading #73 names. What it cannot show: other revisions and the battery case.
- PHYS-9 · A pin probe by an agent and the board. For an agent's live reads (J4), V1.1 versus V1.2 changes the meaning of the same I2C scan: on V1.1 the PMIC is "another device on your I2C bus" (E record `hardware_revisions.v1_1_and_earlier.i2c_pullups`), so a scan with nothing attached can return an address (the PMIC's; its value is · H · AXP313A datasheet not read). On V1.2 there are no pull-ups, so a scan with a part that has none returns an empty list, and the bus does not work at all (E record, same section). The pin map's SDA and SCL are GPIO1 and GPIO2 (E `boards/firebeetle2-esp32s3.json:148-174`). Cheapest rung: the scan at the bench with nothing wired, next to the revision seen by eye. Cannot show: any address of a real part on a breadboard with long jumpers.
