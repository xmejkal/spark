## 1. Findings (POJ-n)

### Existing first: what free tools do for detection, build choice and the erase

- POJ-1 · mpremote `connect auto` takes "the first available USB serial port" and sees only ports with a USB VID/PID; with several boards it picks whichever appears first. `connect list` prints path and USB serial number; `connect id:<serial>` and `connect port:<path>` select one. Licence: MicroPython (MIT, H model knowledge; the docs page states only the documentation copyright). · E https://docs.micropython.org/en/latest/reference/mpremote.html, read 2026-10-13 · supports only: spark must never use `auto` or "try each port" for an erase; `list` plus an explicit `id:` is the reusable part for the two-boards case.
- POJ-2 · Arduino (IDE and arduino-cli) identifies a board by the USB VID/PID of the chip that provides the USB interface, listed per board in boards.txt. A USB-serial bridge (FTDI, CH340) gives the same VID/PID on many boards, so it knows the bridge, not the board; when several known boards share a VID/PID, arduino-cli "tends to just kind of pick one". `board list` has JSON output with port and matching-board candidates. arduino-cli is GPL-3.0. · E web search "arduino-cli board list VID PID detection matching boards ...", results incl. docs.arduino.cc/arduino-cli/FAQ and github.com/arduino/arduino-cli issues, read 2026-10-13 (snippets, pages not opened) · supports only: VID/PID narrows to a family; it cannot tell two near-identical boards apart. Copy the idea of "candidates, not a verdict" and the JSON; do not copy the pick-one behaviour.
- POJ-3 · PlatformIO matches a port to a board by `hwids` (VID:PID) in the board definition; `pio device list --json-output` lists ports with hardware ID and serial number. Known bugs: wrong or oddly-cased hwids break auto-detection, and a user asked for lookup of a port by serial number (a feature request). Licence: not read (H: Apache-2.0). · E web search "PlatformIO pio device list --json-output upload_port auto-detect hwid VID:PID ...", results incl. community.platformio.org, dokk.org PlatformIO docs, read 2026-10-13 (snippets) · supports only: the same limit as POJ-2; a serial number is the better identity where the OS offers it.
- POJ-4 · Thonny's MicroPython installer (esptool inside) asks the person for the port, the file and "Erase flash before installing" (ticked on first install); on failure it tells the person to press BOOT and click Install again. It shows no check of the connected board against the chosen build in the text read. Licence: Thonny MIT (H). · E web search "Thonny MicroPython ESP32 installer dialog target port family variant erase flash ...", results incl. docs.keyestudio.com, wiki.heltec.org, read 2026-10-13 (third-party tutorials, not Thonny's own source) · supports only: the common maker path asks for a port and an erase tick, and checks nothing else. This is the baseline spark must beat under D4, and the competitor (PO-16).
- POJ-5 · ESP Web Tools (Apache-2.0) reads the chip family from the board and picks the build from a manifest listing one build per chip family (ESP32, S2, S3, C3, ESP8266); an optional `serialType` separates native USB CDC from a USB-UART bridge. The page fetched gave nothing on its erase choice or any confirmation. · E https://github.com/esphome/esp-web-tools, read 2026-10-13 (README level only) · supports only: "detect the chip, then offer the build from a table keyed by chip" is the model for D4's "offer the matching firmware base". Whether the manifest encodes flash size or PSRAM — (not read).
- POJ-6 · The nearest repository fact for build choice: MicroPython's page for ESP32_GENERIC_S3 offers a Standard build ("most ESP32-S3-based boards with 4MiB or more of flash") and a `spiram-oct` build "if your board has Octal SPIRAM". spark's board record names only `micropython_port` "ESP32_GENERIC_S3" and the tools list pins the standard file. · E council/tech-lead.md PHYS-5 (the page read 2026-10-13 by the tech lead); boards/firebeetle2-esp32s3.json `micropython_port`; data/tools.json `micropython-esp32s3` `file` · supports only: a build choice that depends on PSRAM is a fact the record does not hold and that the PO's N16R8 may need. Which build the N16R8 needs is — until the bench.
- POJ-7 · What none of these do for a script or an agent: Thonny is a GUI; ESP Web Tools is a browser page; Arduino and PlatformIO return a port list, not an "is it safe to erase" verdict. Only mpremote and esptool, and the two list commands (`board list`, `device list`), are scriptable. No tool read does a pre-erase confirmation that an agent can be held to; the confirmation is the person's click (Thonny) or nothing. · H (Claude's reading of POJ-1 to POJ-5) · supports only: the safe-erase gate is spark's own to build, in code, with a `--json` answer; nothing to reuse.
- POJ-8 · Reuse and do not copy: reuse esptool read-only commands (`read-mac`, `flash-id`; and per the tech lead, `get-security-info` and eFuse reads are listed in esptool source, TL-3, not run by me) and mpremote `connect list`/`id:`, both already in the tools list. Do not copy: first-port or first-device selection (POJ-1, POJ-2), VID/PID as proof of the board (POJ-2), the erase as an unconfirmed default tick (POJ-4), a table keyed only by chip family (POJ-5), as that would call an N4 and an N16R8 the same board (boards/firebeetle2-esp32s3.json `//sku`). · H · supports only: a design input, not a decision.

### D5 existing first: two nearly identical boards, OTA, and a host-to-board contract

- POJ-9 · Two nearly identical boards on one computer: what can tell them apart. The chip's MAC (esptool `read-mac`; MicroPython `machine.unique_id()` is the MAC, per TL-6) is unique per chip; the USB serial number appears in `mpremote connect list`; the port path is not stable (it changes after the flash on the S3's native USB: PHYS-1, USER-3). For an ESP32-S3 on native USB the USB serial number is believed to be the chip's MAC (H, model knowledge, not read), which would tie the two together. · E for the tools and the unstable path (docs.micropython.org mpremote page, read 2026-10-13; council/user.md USER-3, USER-12; council/tech-lead.md TL-6); H for serial = MAC · supports only: identity for two boards must be MAC or serial, never port or "first found"; the project needs a stored identity to pin to (a new fact, see POJ-19).
- POJ-10 · The current code does not guard that case: with no `--port`, esptool "tries each port" and erases the first board it reaches, and a chip name does not tell two S3 boards apart. · E scripts/deploy.py:166 (help text), :113-119; council/user.md USER-1 · supports only: D4 needs a port-and-identity pin before any erase.
- POJ-11 · ESPHome OTA: authentication is by a pre-shared key (Noise NNpsk0, the same key as its native API) or a legacy password; a "safe mode" is enabled by default and helps recovery when an update fails. The page read did not say how a binary is matched to the board's platform, nor the rollback mechanism, nor the licence. ESPHome targets a device by its configured name through the dashboard and CLI. · E https://esphome.io/components/ota/esphome/, read 2026-10-13 · supports only: the pattern "a key the project and the board share, and a recovery mode" is how a mature tool handles update safety; the details are — (not read). ESPHome compiles the firmware itself from a YAML, which spark does not (P56).
- POJ-12 · ArduinoOTA and `espota.py`: authenticated by Digest-MD5 with a password, integrity by an MD5 checksum, target by hostname and port set in the sketch (`setHostname`, `setPort`, `setPassword`). Nothing found on two boards with the same hostname, only that names must be unique (H, from the missing result). The ArduinoOTA code is LGPL (H, model knowledge, not read). · E web search "MicroPython WebREPL security password file transfer; mip install; ArduinoOTA hostname password espota.py same hostname two boards", results incl. arduino.readthedocs.io and espwifi.readthedocs.io OTA pages, read 2026-10-13 (snippets) · supports only: the board must hold a name and a secret that the project knows before any OTA is possible; so OTA needs a first wired flash that installs both.
- POJ-13 · MicroPython WebREPL: a password (from `webrepl_cfg.py`, stored on the board's filesystem) over WebSocket; file transfer by client scripts; third-party sync tools (mwrsync). `mip install` fetches packages from micropython-lib or GitHub onto the board. Neither is MicroPython's firmware OTA: no partition swap, no rollback in what was read. · E same search, results incl. github.com/Hermann-SW/webrepl, pypi.org/project/mwrsync, docs.openmv.io webrepl, read 2026-10-13 (snippets); E for mip install forms in the mpremote page (round 1 PO-4) · supports only: "update over the air" for MicroPython today means file sync over WebREPL or a Wi-Fi client script running on the board, not a firmware swap. Its security rests on one stored password in plain text on the board (H, from the forum snippet).
- POJ-14 · Firmware-level OTA needs an OTA partition pair plus `otadata`; the partition table in the kept v1.29.0 ESP32_GENERIC_S3 .bin has only `nvs`, `phy_init` and `factory` (0x10000, 0x1f0000); so there is no OTA slot in the image spark builds. · E council/tech-lead.md TL-14 · supports only: firmware-level OTA is not a small step from today's chain: it needs a different partition layout and so a different image than the one Wokwi passed. That breaks the guard "flash only the image that passed" unless the simulated image changes too (round 1 PO-7).
- POJ-15 · Is there a protocol between the spark plugin and the board's firmware today? No. The only contract is the text line `ready`, which the firmware prints at boot and a person reads in the REPL. Nothing in the image names the project, the board file, the pin map or the image sha256. · E scripts/deploy.py:11, :187; commands/build.md "ready contract" (as cited in scripts/deploy.py); scripts/flash_image.py (the image holds MicroPython and the project's files, no identity file found in the lines read) · supports only: a host-to-board contract does not exist; any identity the plugin wants from a board it must ask of esptool (hardware) or of the filesystem (via mpremote).

### The use cases, simplest to most advanced (one line each: value, risk removed)

Each UC is a proposal for the PO to confirm. "Safe" is D4: nothing erased or written that was not checked, never without the person's yes.

- POJ-16 · UC1 · One board, plugged in, nothing else attached: spark finds it, says what it is, and says it is the one the project is for (chip, flash size, MAC), then asks the yes, then flashes the image that passed. Value: J1 with no guessing of a port. Risk removed: erasing a board nobody named; a flash that the person cannot account for. · H · supports only: the walking skeleton (POJ-24).
- POJ-17 · UC2 · One board, but it differs from the project's (another chip, the N4 instead of the N16R8, an unknown board): spark says what differs and refuses by default; it lists what it can do (stop; use the matching board record if there is one; a general board record; go ahead anyway, with a named ignore flag). Value: J3. Risk removed: a wrong-board erase and wrong pins. Precondition: the board record holds machine-readable flash and PSRAM (TL-1: they are prose today). · H; E for the missing fields (TL-1) · supports only: P219.
- POJ-18 · UC3 · The right chip, but the build is not the right one (PSRAM): spark names the MicroPython build the board needs, offers to fetch it (the tools list already downloads one file with a sha256) and builds a new image that must pass again. Value: D4's "offer to download the firmware base". Risk removed: a flash that boots without PSRAM, or not at all. · H; E for the existing download mechanism (data/tools.json `micropython-esp32s3` with `url` and `sha256`) and the two builds (POJ-6) · supports only: a new tools entry, a record field (`micropython_variant`?), and the re-run of the simulation (paid minutes).
- POJ-19 · UC4 · Two nearly identical boards are plugged in: spark lists both with MAC, serial number, flash size and what project each was last flashed for; it never erases without a named choice; and it remembers the choice in the project (the MAC of "my board"), so the next deploy refuses the other one. Value: D5. Risk removed: erasing the board that runs the PO's other gadget. Needs: a project-held identity fact (the MAC from the first successful read, in the PO's `.spark/`, H) and a place for "last flashed for" on a board (POJ-22). · H · supports only: a proposal; whether the MAC should be stored in the project is a decision for the PO (Q-j).
- POJ-20 · UC5 · After the flash, spark checks the board started: for Claude, a machine-readable `ready` seen over a REPL or serial read (no human Ctrl-C). Value: J1's proof that Claude can state. - POJ-21 · UC6 · An update of one firmware file on a board that boots: copy it with mpremote, after the same check of the board and a gate that names the passed run (round 1 PO-7, PO-21). Value: J2. Risk removed: a full erase for a one-line change; an unsimulated file on the board. · H · supports only: needs the decider's answer on the gate.

### Risks: the riskiest belief under D4, its test, and the pre-mortem

- POJ-26 · Riskiest belief under D4: that the facts spark can read from the connected board (chip, flash size, MAC) are enough to tell it is the board "the project is for", so that a pass of the check means "safe to erase". They are not: a V1.1 and a V1.2 of the same SKU read identically (boards/firebeetle2-esp32s3.json:300), the PSRAM size is not in the commands read (POJ-8, round 1 PO-9), and a MAC says which chip, not which project. A "matches" that means "the same chip and flash size" can pass for a wrong board. · E for the three limits; H for the conclusion · supports only: the check's words must say "chip and flash match", never "this is your board".
- POJ-27 · Cheapest test: a bench step with two boards, or with one board and a deliberately wrong record. Run the read-only commands against the PO's board; compare the output with the record's `chip` and SKU text; then change the record to the N4 and see whether the check says "flash differs". Pass line, set before the run: the check refuses with a named difference in both cases and writes nothing to the board. If the PO owns a second ESP32 board (the FireBeetle C6 is mentioned in USER-13), plug both in and see whether `read-mac` and `connect list` name them differently. · H · supports only: a bench step of under an hour; nothing flashed.
- POJ-28 · Pre-mortem, the safe design, six months on, failed. Each H (Claude):
  1. The check passed and the board was still wrong: a revision difference or a wiring difference was invisible to it (POJ-26); the person trusted "checked".
  2. The check was a hurdle: the person always passed the ignore flag, and the agent learned to pass it as well, so D4 was met in word only. The flag must not be a silent default for an agent.
  3. The MAC pin made the project fragile: the PO replaced the board, the project refused, and nothing said how to re-pin; the safe rule felt like a lock.
  4. The build download made a new image (spiram-oct), which was never simulated, and the flash went to the board untested, or the simulation was re-run for every board change in paid minutes and the PO stopped using it.
  5. "Offer a better board" turned into a table of boards (a chip table), which AGENTS.md and P192 struck for one board (round 1 PO-31, issue #144 "NOT: a chip table").
  6. The host-to-board contract grew (names, keys, an identity file) before one person used OTA; it was code that no gadget needed.
  7. Two boards were found and listed, but the person had no way to tell which was on the desk (a MAC means nothing to a person): the list needs a visible action (unplug one and re-list; or the board blinks its LED, which is behaviour).
- POJ-29 · The question about P221 against the vision's not-goal. scrum/VISION.md lists "Arduino or ESP-IDF before a design pulls them" (F1, F2 parked). The PO, 2026-10-13, asked for a P221 spike (#203) and named Arduino and PlatformIO. Nothing in this lens decides it. The question is for the PO: Does D-something lift the not-goal for the spike's reading only, or does a design pull it? And does the spike run now, or after the first safe board on the bench? · E scrum/VISION.md "Not goals"; #203 body · supports only: Q-m below.

### Host-to-board contract (D5), as options and not as a design

- POJ-30 · What a contract could hold, from what exists, proposed only: (a) read by the host from hardware: chip, flash, MAC (esptool); (b) read by the host from the filesystem: a small facts file written into the image by `flash_image.py` (the project, the board id, the pin-map's hash, the image's sha256), read back with `mpremote fs cat`; this is a fact export, in line with AGENTS.md; (c) printed by the firmware at boot: the `ready` line already, which could carry the same id (this touches the firmware, which the conversation writes; so it is behaviour and spark's check would only look for it); (d) a board name and secret for OTA (POJ-12), which is behaviour plus a secret and so the latest. Option (b) lets "what is on this board" be answered without the firmware's help and lets a re-flash tell "this board holds another project's image" before the erase. Cost: a new file in the image changes the image's sha256, so it is part of what the simulator tested (a free change, since the image is built before the scenario). · H; E for the image build (scripts/flash_image.py: littlefs files at 0x200000) · supports only: option (b) is the smallest thing that answers "which project is on this board" and removes the blind erase. Whether to build it — Q-k.

### D6: a known board should be seamless and still sure (existing first, then the main journey)

- POJ-31 · How known-device tools make an update seamless. ESPHome targets a device it already has a configuration for (by its configured name, through the dashboard or CLI), authenticates the uploader by a shared key (or a legacy password), and has a safe mode that helps recovery when an update fails; the page read did not say how it checks the binary against the board or how rollback works. Tasmota (read only through ESPHome's migration guide and forum snippets) uses a minimal firmware as a stepping stone and, on newer ESP32, a safeboot partition; skipping a stated option when moving to ESPHome "will soft-brick" the device by blocking later OTA. · E https://esphome.io/components/ota/esphome/ and the search "Tasmota OTA upgrade minimal firmware safeboot verifies chip type; ESPHome dashboard update known device compare firmware" (results incl. esphome.io/guides/migrate_sonoff_tasmota, community.home-assistant.io), read 2026-10-13, snippets · supports only: "seamless" in these tools rests on three things set up once: the device is known by name, it holds a key, and a recovery path (safe mode, safeboot partition) exists on the device. Their checks are silent when they pass; they speak when the key, the name or the space is wrong (a Tasmota upgrade can fail from lack of storage, neilturner.me.uk snippet, E). What each checks about the board type: — (not read).
- POJ-32 · The lesson for spark, as H: knowing the board is a record spark writes the first time, and an update trusts the record only while cheap checks still agree with it. spark has no on-board recovery path: the S3's ROM bootloader and native USB give one by cable (BOOT and RESET, PHYS-2), which is why a wired update can be seamless without a safe mode on the board. The seamless part is the checks that stay silent; the sure part is that each check reads the board and compares it to what was recorded, not to what the person says. · H (Claude, from POJ-31, PHYS-2) · supports only: the known-board path below.
- POJ-33 · What "known" would mean in spark, as a proposal: the board answered the identity check once (chip, flash size, MAC read; Q-j's stored MAC) and a successful `ready` was seen after the last flash; the record of that is a line in the project, with a date. An update then repeats only the cheap, read-only checks (the port still holds the stored MAC, the chip and flash size are the same, the image is the one a passed run names, the files newer than the image are named), prints nothing but one line when they all pass, and goes on without a question for the same image over the same layout. It stops and speaks when any check differs, when the stored identity is missing, or when the update would change what D4 protects (erase of a board that holds another project's files, a new build). Is the yes still asked for an erase of a known board? D6 says "seamless", D4 says "never without the person's yes" — Q-q. · H, with E for the checks' tools (POJ-8) · supports only: the main journey row; the answer to Q-q.
- POJ-34 · Risk of seamless: a silent pass that is wrong is worse than a noisy one (POJ-26). The board that is "known" may have been swapped for an identical one on the same port; only the MAC catches this (POJ-9). A board that was changed by hand (the person used Thonny) is still "known" by MAC but holds something else; only reading the facts file (contract option b, POJ-30) or a file listing catches it. So the seamless path needs, at least, the MAC read each time. Cheapest test: the two-board bench (POJ-27), and a bench step that flashes by hand with another tool and then runs the update. · H; E for the MAC point (POJ-9) · supports only: Q-r.

## D7: existing tools for a live REPL

Existing first only. The PO, D7 (brief.md): "...access the repl directly frm claude if the board is connected, or on the same wifi, maybe we/claude can try things live on the board". Read 2026-10-13; the three searches returned snippets, no page was opened. Nothing here is a design.

- POJ-35 · mpremote from a script: runs on the host over USB serial (or a network serial, `connect` with RFC2217 per the docs list in round 1 PO-4/POJ-1), with `exec` (run Python text, print output), `run` (a local file in RAM, after a soft reset, `main.py` not run), `fs cp/ls/rm`, `mount`, `soft-reset`, `resume`. Guards: it only auto-detects USB serial ports and, with several boards, takes the first; it asks nothing and does not limit what code runs. Licence: MicroPython's (MIT, H). It is already in spark's tools list pinned at 1.29.0. · E https://docs.micropython.org/en/latest/reference/mpremote.html (read 2026-10-13); data/tools.json mpremote entry · supports only: the cheapest live channel for an agent over a cable is already installed; the guard (device chosen by `id:`, what code may run) is spark's to add.
- POJ-36 · An MCP server for MicroPython exists as a Claude plugin: "A plugin to interact with micropython devices within Claude" (fingerskier-micropython-claude-plugin, on claudepluginhub.com). Per the snippet it starts an MCP server in an isolated venv, ships mpremote, and offers tools `list_devices`, `connect`, `disconnect`, `device_info`, `list_files`, `read_file`, `write_file`, `delete_file`, `mkdir`. What it guards, whether it can execute code, and its licence — (page not opened; the listing is a third-party catalogue). · E web search "MicroPython MCP server REPL agent board mpremote Claude", result claudepluginhub.com/plugins/fingerskier-micropython-claude-plugin, read 2026-10-13, snippet · supports only: a ready-made agent surface may exist; its safety (no identity check seen in the tool names, a `write_file` and `delete_file` on any connected device) is the kind of unguarded access D4 forbids. - POJ-37 · belay (Python library, Apache-2.0, by Brian Pugh, requires Python >= 3.8, on PyPI): decorated host functions are sent to the board and run there; it also has a command-line tool and a package manager for MicroPython projects; it supports a wired USB serial connection and wireless connection over WebREPL on Wi-Fi. What it guards (identity, confirmation) — not stated in the snippets. · E https://github.com/BrianPugh/belay and https://pypi.python.org/pypi/belay (search snippets, read 2026-10-13); connections page belay.readthedocs.io/en/v0.4.0/Connections.html (title only) · supports only: belay is the one free tool read that covers both cable and Wi-Fi from a script with a Python API; it is a new dependency beside mpremote ("one tool per job"), and its function-to-board model is code written for the board (behaviour), not facts.
