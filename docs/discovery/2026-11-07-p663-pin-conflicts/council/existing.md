### In spark

- EX-1 · The assigner knows five kinds of "taken", each in a different place and none as a claim with an owner: (a) `taken_gpio`, a local set of GPIOs it placed itself (`assign` builds it, `scripts/assign_pins.py:250`, filled at :285 and :313); (b) the `strapping` role, which hides a pin from the candidate list (`UNAVAILABLE_ROLES` :67, `candidates` :156-168) and refuses a named pin (:259-263, text :70-72); (c) a role penalty for onboard parts and the console (`ROLE_PENALTY` :82-90, `CONFLICTING_ROLES` :112), which ranks a pin worse but leaves it usable; (d) bus sharing (`SHARED_LINES` :188, `bus_holders` :250, :272-280) and the SS exception (:281-283); (e) `bus_line` and `board_dedicates_pins_to` (:182-209) for bus lines. ### Outside spark

- EX-16 · ESPHome (esphome/esphome, `esphome/pins.py`) does two checks relevant here. (1) Duplicate use: `PinRegistry.final_validate` groups every pin use by pin; if a pin is used more than once and not every user sets `allow_other_uses: true`, it raises `Pin <n> is used in multiple places`; if it is used once but the flag is set, it raises `Pin <n> incorrectly sets allow_other_uses: true`. A pin's schema takes `allow_other_uses` as an optional boolean; `remove_optional_conflicts()` lets an "optional" pin give way. (2) Strapping: `check_strapping_pin` logs a warning "GPIO%s is a strapping pin and should only be used for I/O with care" unless `ignore_strapping_warning` is set, and raises if that flag is set on a pin that is not a strapping pin. Does not: no connector, no onboard-part ownership, no explanation of who the other users are beyond the pin number, and strapping is a warning there while spark's C4 refuses a named one. License: ESPHome's LICENSE says the Python code and everything outside C/C++ files is MIT, C++ runtime is GPLv3. Reuse: the published behaviour (a per-claim "sharing is allowed" flag that must hold on every claimant, plus a check that the flag is not stale) can be restated from the description; the Python file is MIT so it could be copied with notice, but spark's records differ. · E · https://raw.githubusercontent.com/esphome/esphome/dev/esphome/pins.py (read 2026-11-07, via a fetch summary; lines 422-433 confirmed by grep for the strapping function); https://raw.githubusercontent.com/esphome/esphome/dev/LICENSE (read 2026-11-07) · supports: the decision "reuse an outside approach for sharing and strapping, or not".

- EX-17 · KiCad's ERC compares pin types on a net against a "Pin Conflicts Map": a configurable matrix of which pin-type pairs may connect, with error, warning or ignore per cell; by default an output tied to an output is an error. It works on schematic nets with typed pins, not on a board's GPIOs, and it has no concept of a connector's fixed routing or a strap. Third-party reference calls the check `pin_to_pin`. License: KiCad is GPL (H, not read this session); its docs say the user can edit the map in Schematic Setup, Electrical Rules. · E (docs.kicad.org/10.0/en/eeschema/eeschema.html named in search results, text not opened) / H for license · search result summary 2026-11-07 · supports: the decision "a severity matrix per pair of claim kinds (K1-K7) or a fixed one". Caveat: matrix cell values not confirmed by me.

- EX-18 · Zephyr devicetree pinctrl: the search found no build-time error for one pin claimed by two nodes. The material found says pin conflicts are checked by hand, that a conflict is resolved by remapping a pin or disabling the other node, and that overlays can silently override a property (last one wins). So Zephyr offers a data model (pinctrl states per node) but no general duplicate-claim check in what I found. Absence of a finding is not proof of absence. · E (search result summaries only; pages not opened) · https://interrupt.memfault.com/blog/practical_zephyr_05_dt_practice and https://www.embeddedsoft.net/fixing-zephyr-devicetree-overlays-that-silently-fail/ · supports: "no standard detector to reuse here".

- EX-19 · PlatformIO, Arduino variants, MicroPython and CircuitPython board definitions: as I know them, a board definition names pins (Arduino `pins_arduino.h` constants, MicroPython `pins.csv`, CircuitPython `pins.c`) and flags a few (strap, LED, button names); they carry no claim-conflict check. Spark already reads the Arduino variant header for transcription checks (scripts/check_vendor_pins.py:1-30). · H · model knowledge, no source read this session (no search made for it) · supports: only the statement "no outside definition format found that records connectors-as-fixed-pins and checks them"; treat as unverified.
