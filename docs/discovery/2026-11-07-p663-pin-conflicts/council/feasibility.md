## Findings

Tracing a claim on a pin

- FE-1 · One function, `assign_pins.assign(board, signals)`, places every pin, and four callers each run it on their own: `assign_pins.main` (scripts/assign_pins.py:537), `pin_module_for` (:499), `emit_board.read_inputs` (scripts/emit_board.py:1088) and `breadboard._unwired` (scripts/breadboard.py:315). The board file, the pin map, and the sheet's "nothing wired yet" lines therefore all follow one change to the assigner. · E · the grep of `assign_pins.` over scripts/ · supports: a conflict model placed at the assigner reaches `pins.py`, the board file and the sheet without touching each of them.
- FE-2 · The sheet and the Wokwi diagram do not call the assigner. They read the built circuit: the sheet reads `dist/board/circuit.json` (scripts/breadboard.py:38, :70), and the diagram is converted from the same build in `check_spine.convert` (scripts/check_spine.py:553-570, `tools/circuit-to-wokwi`). The pins reach them through the traces `emit_board` writes from the assignments. · E · those lines · supports: a pin moved in the assigner moves in the sheet and in Wokwi with no code there. But a "plug the ribbon cable" line is new sheet code: `breadboard._wiring` (scripts/breadboard.py:263) lists a wire for every trace, and nothing marks a trace as a cable. Whether Wokwi needs to differ for a cable is H (electrically the same net, so likely no): untested.
- FE-3 · `design.signals_of` (scripts/design.py:381-421) is the one place the signal list is built. A person's pin for a part's signal already enters here: `pin_part_signals` (scripts/design.py:346-378, P513) sets `pin` on the part's signal from a top-level `signals` entry. The assigner then treats a `pin` as "dedicated hardware, not a choice" and honours it first (scripts/assign_pins.py:249-293). This is how the P581 walk pinned 4 of the 5 GDI signals. · E · those lines; walk row 2 (~/Development/spark-walks/p581-sound-joystick/p581-rows.md) · supports: placing a connector's pins first can reuse the pinned-signal path. The change is to derive the pins from a record instead of from the person's typing. The cost is that a connector pin needs a "strap accepted" flag on the pinned path.
- FE-4 · The strap refusal is one line in the named-pin loop: `blocked = [role ... in UNAVAILABLE_ROLES]` then `raise Impossible(NAMED_STRAP_REFUSAL ...)` (scripts/assign_pins.py:262-265). P527 is a bypass of that one `if` for a pin marked as fixed by a connector. The unpinned path never offers a strap (`candidates`, scripts/assign_pins.py:166-167 skips `strapping`), which C4 keeps. · E · those lines · supports: P527 is a small change if the "fixed by a connector" mark arrives on the signal.
- FE-5 · Nothing reads the GDI facts. `gdi_on_firebeetle2_s3_gpio`, `gdi_used_signals`, `gdi_connector_pin_order` and the `host_requirements` line ("these pins are taken, do not give them to another part") sit in the part record (tests/data/parts/dfr0664-tft-2in.json; the shelf copy is ~/.local/share/spark/shelf/dfr0664-tft-2in.json). The only reader of `host_requirements` is the sheet, which prints it as text (scripts/breadboard.py:340). A grep of scripts/ for `gdi_on_firebeetle2` finds no code. · E · `/usr/bin/grep -rln "gdi_on_firebeetle2\|host_requirements"` · supports: the data exists and is unread; K1-K3 need no new part fact if a reader is added, but the key name carries the board id (`..._on_firebeetle2_s3_gpio`), which a general reader cannot walk without a rule (see FE-11).
- FE-6 · Reproduced today. The three-part P581 design (dfr0664-tft-2in, max98357a-dfr0954, joystick-module-mh) on `firebeetle2-esp32s3` places 15 signals and exits 0. I2S_BCLK is on GPIO18 (the GDI CS), JOY_SW on GPIO9 (the GDI SD CS), TFT_BL on GPIO38 (the GDI RST), and TFT_DC, TFT_CS, TFT_RST, SD_CS on GPIO12, 11, 13 and 14. Nothing is flagged. SCLK, MOSI and MISO land on 17, 15 and 16 because those are the board's SPI pins. · E · `python3 scripts/assign_pins.py <scratch>/req.json --project ~/Development/firebeetle-games`, exit=0 · supports: K1 is silent today, and the bug is in the assignment, not only in the check.

What the refusal carries

- FE-7 · When the assigner refuses, it raises `Impossible(str)`, prints "cannot place every signal on this board:\n\n  <sentence>" and returns exit 1 (`EXIT_IMPOSSIBLE` is `EXIT_PROBLEMS`, scripts/assign_pins.py:52, :539-540). With `--json` the refusal is still that text, not JSON: the JSON object is printed only on success (:557-562). There is no code, no kind, no second claim as a field. The "already taken" sentence names the asking signal and the pin, and not the signal that holds it (scripts/assign_pins.py:283). · E · reproduced: a strap by name gave the NAMED_STRAP_REFUSAL text with exit 1, and a duplicate pin gave "X asks for D6 (GPIO18), which is already taken" with exit 1; both with `--json`, both plain text · supports: J5 is not met today; a conflict as data is new output, not a field to read.
- FE-8 · The same refusal is a different exit code in the other callers. `emit_board.read_inputs` turns `Impossible` into `RefusedInput(SCHEMATIC_STAGE, str(...))` (scripts/emit_board.py:1089-1093), and `check_spine.run` turns that into `Stage("schematic", COULD_NOT_RUN, text)` (scripts/check_spine.py:408-411). So an unplaceable pin is exit 1 from `assign_pins.py` and "could-not-run" (exit 2) from the spine, with the whole refusal as one `detail` string. The brief's "must not get worse: the exit codes" has to cover both. · E · those lines · supports: the design must pick one status for a left conflict, and each caller's mapping must stay as it is or change on purpose.
- FE-9 · The core already has the shape a conflict needs. `Finding(severity, subject, code, sentence, fix)` and `NextStep(op, argv, why, effects, needs_yes, needs_person, env)` (scripts/spark/core/result.py:12-22), `SparkError(template, code, fix, status)` (scripts/spark/core/errors.py:8-17), and `envelope_item` as the one renderer. A conflict kind would be the `code`, the pin the `subject`, and the question a `NextStep` with `needs_person`. · E · those lines · supports: no new envelope is needed. Not wired: `assign_pins`, `emit_board` and `check_spine` are scripts, not Operations (the Operation list found: board_codes, board_envelope, deploy_service, grant, spark/bench/*), so a conflict as a Finding in the pin assigner waits on porting the assigner. `Finding` has one `subject`, so "both claims" needs the sentence or an added field (—, not tried).

Where a connector's pins and the person's answer enter

- FE-10 · The board record has no connector today: `boards/firebeetle2-esp32s3.json` has no `connectors` key (printed keys: schema ... pins, wake_capable_gpio, adc_gpio, pin_roles, deep_sleep, vendor, hardware_revisions, documents, power). P460 (#628) is the open spike that holds the class diagram `Connector`, `ConnectorPin`, `ConnectorPlug`, a part's `plugs_into`. P527 and #892 depend on it. · E · `python3` key listing; `gh issue view 628` · supports: any connector design waits on, or restates, P460's answer. The board's other facts of this kind already have a home to copy: `pin_roles` with `gpio` and `note`, read by `roles_of` (scripts/assign_pins.py:151), validated in `boards.validate` (scripts/boards.py:719, role names against `PIN_ROLES` at :783-786), and onboard parts through `boards.ONBOARD_ROLES` and `onboard_entries` (scripts/boards.py:351-374).
- FE-11 · Two homes for "the screen's pins on this board" exist and disagree in shape. The part record holds them under a board-named fact key (`gdi_on_firebeetle2_s3_gpio`, unverified, "read off the board's schematic image"), keyed by the module's own signal names (BL, SCLK, ..., RES, SDCS). The part's `needs` use different names (TFT_RST for RES, TFT_BL for BL, SD_CS for SDCS; SCLK and MOSI the same). A reader needs a name map either way. If the connector lives on the board record, as P460 proposes, the map is the connector's pin names against the part's `gdi_connector_pin_order` (VCC, BLK, GND, SCLK, ...). Which is the home is a decision (Questions). · E · tests/data/parts/dfr0664-tft-2in.json `needs` and `facts` · supports: "records grow by need" and "checks read facts, not logic per part" (AGENTS.md) favour one board-side `connectors` fact plus a part-side `plugs_into`; the name map is the cost.
- FE-12 · The requirements file already holds a person's choices per part, and tools preserve what they do not know. A parts entry is a string or `{"part", "name", "rails"}` (scripts/design.py:198-222, `rails_requested` :225-248); `needs._merge_parts` keeps "a name, `rails` and any other key" (scripts/needs.py:657-689) and `dict(held, ...)` keeps other top-level keys (scripts/needs.py:~800). So "cable or wires?" has a natural home: a key on the part's entry, for example `{"part": "dfr0664-tft-2in", "connect": "gdi"}`, which `parts.py --requirements` does not drop. `design.read` and `requested_parts` do not refuse unknown keys on a parts entry, so the key needs its own validation. `design.read` validates only `signals` and `parts` shape (scripts/design.py:114-166). The brief's open question "where does the answer live" is thus answerable from the code: the requirements file, per part. The project folder also holds `.spark/project.json` with a `decided` list that "no script reads" (~/Development/firebeetle-games/.spark/project.json, the `//decided` note). · E · those lines · supports: a store of the answer needs no new file. A run that is asked has to write the answer (an Operation that writes `requirements.json`), which no assigner path does today.
- FE-13 · The two questions are a flow, not a function: the assigner is a pure function with no person in the loop. "Ask once, keep the answer" needs (a) a refusal that names the question as data (FE-7), (b) a caller that asks and writes the answer into requirements.json, (c) a re-run. In Claude Code the caller is the agent. In the CLI it is a prompt or an exit code with the question printed. The core has `ASKS` and `needs_yes` for deploy and grant (scripts/spark/core/operation.py: `READS, RUNS, BOARD, DELETES, WRITES, ASKS`; `NextStep.needs_person`) as the pattern. · E · those lines · supports: the pattern to copy exists; nothing for it exists in the pin chain.

What the spine checks

- FE-21 · `check_spine.py` has no stage that compares pins. Its stages: board, parts, schematic, footprint, build, islands (`islands_in`, scripts/check_spine.py:285-342, which finds no ground, a terminal on nothing, and an unfed supply), then simulation. A check that "reads the record's taken pins" (option C, the safety net in D1) is a new stage or a new item in `islands_in`'s spirit, over the same data. Where it would sit: after the schematic stage, reading `inputs.assignments` (already in hand, scripts/check_spine.py:407) against the connector record, before the slow build. `check_spine` calls `emit_board.read_inputs` for the assignments, so no second assign run is needed. · E · scripts/check_spine.py:401-411 · supports: option C is a cheap check on data the spine already holds; cost is the stage and the fixture.
- FE-22 · `--keep` writes `firmware/pins.py` by running `assign_pins.pin_module_for` a second time (scripts/check_spine.py:948-975). Row 5 and row 7 of the walk (BUILD_TIMEOUT_S 300 s; a kept stale `board.tsx`) show a conflict model that changes a pin map must also regenerate `board.tsx`, which `--keep` leaves alone ("delete it to have it regenerated"). So after a cable answer changes pins, the kept board is stale. P664 (#893) is filed for the timeout. · E · walk rows 5, 7; scripts/check_spine.py:948-975 · supports: a risk to the done-when "the sheet names the cable and the strap of GPIO3" on a project that already has a kept `board.tsx`.
