Written before the run (D2: predictions first; D7/D8: the PO chose to research one of his own boards). The route is
the documented one: docs/guide/how-it-works.md "Your own dev board", five steps, in a scratch project AND a scratch store (SPARK_HOME, HOME and TMPDIR each a separate word, inside the scratch folder; the real store untouched — verified by its file times) with spark
0.8.1 (a8aa34d). The runner is a fresh agent that reads only the plugin's documents; the scorer is not the runner.

## Predictions (the facilitator's, 2026-10-09, before the run)
- P0.1 Step 1 (copy the S3's definition, take the pin map from the vendor's `pins_arduino.h`): the arduino-esp32 variant for DFR1075 exists and `gh` fetches it; the pin map lands in under 20 minutes. Confidence: 70%.
- P0.2 Step 1's "measure the header geometry again from the vendor's drawing": DFRobot's DFR1075 wiki shows a dimension picture but no CAD/PDF drawing a script can parse, so the geometry is read off a picture (H numbers) or left as the S3's copy — the record carries at least one number with no provenance better than "stated from a picture". Confidence: 75%.
- P0.3 Step 2 `boards.py --validate`: passes once the id matches the file name; at least one refusal on the way about a name or a decision leaking into the facts file. Confidence: 60%.
- P0.4 Step 3 `emit_footprint.py` writes a footprint from the copied/measured header; step 4 `check_vendor_pins.py` passes if P0.1 held. Confidence: 65%.
- P0.5 The chain on a trivial requirements file (the new board + one LED) reaches `[ok] build` with tscircuit — or stops at the footprint naming a field. Confidence: 50%.
- P0.6 At least three gaps in the documented route are found (candidates: boards/README's steps are the bin's — P127; no step says which Wokwi part type stands in for a C6 board; the deep-sleep/power facts have no documented source for a new board; nothing says where a project's board file is written when there is no project yet). Confidence: 80%.
- P0.7 Wall time over 60 minutes. Confidence: 70%.

## The run (the runner's report, 2026-10-09 18:15–18:29, 14 minutes; the full text is in council/round-0-runner.md)
- Steps 1–4 pass on the final file: `boards.py --validate` and `--for-fab` ok (exit 0); `emit_footprint.py` writes the module (32 plated holes); `check_vendor_pins.py` → `ok (20 pins against espressif/arduino-esp32 variants/dfrobot_firebeetle2_esp32c6/pins_arduino.h)`.
- Step 5 (`check_spine.py requirements.json --keep .`, the board + `led-red-5mm`): board ok · schematic 7 traces · footprint ok · `[ok] build 5 trace(s), 0 errors, tsci 0.0.2621` · `[!!] simulation no diagram was produced: "14" is not a pin of board-esp32-c6-devkitc-1` — the Wokwi stand-in has no GPIO14 and the assigner put the LED on D3 = GPIO14; no document says how to state a stand-in's missing pin → STOP (G0.6). Exit 1, "the chain is broken".
- A SHORT the checks missed (G0.3): a first version of the file named pads by bare GPIO numbers; validate, --for-fab and the footprint all passed; tscircuit then read the numbers as pin numbers and joined 3V3 to the pad printed "17" (RX) and GND1 to "15" (the LED). The chain reported only an unrelated open terminal.
- A plugin-folder write (G0.7): the live `check_vendor_pins.py` created `<plugin>/.spark/cache/dfrobot_firebeetle2_esp32c6.pins_arduino.h` despite SPARK_HOME and HOME redirected; later `--offline` runs read it. The real store stayed untouched.
- Every number in the record carries a provenance: the dimension drawing is a VECTOR PDF (no text layer) that the runner parsed geometrically (12.712 pt/mm calibrated on the 60 mm outline): width 25.4 (stated; measured 25.38), pitch 2.5399 measured, row spacing 22.845 (= 9 × 2.54), pad 1.501, holes 2.001 at 1.699 inset; the pin map from pins_arduino.h; wake/ADC/strapping from the C6 datasheet v1.5 and soc_caps.h; deep sleep 36 µA (the wiki's higher of two revisions; the chip alone 7 µA datasheet-typ); `regulator_3v3_a` null (not read); `wokwi_part_type` from memory, accepted by the converter.
- Ten gaps G0.1–G0.10 in the documented route (council/round-0-runner.md): the variant folder's name guessed; the `physical` schema undocumented; `header_order` labels outside the naming rule (→ the silent pad merge); `pad_aliases` undocumented and ineffective here; the closed `pin_roles` list undocumented, `//` refused inside it; the stand-in's pins unknowable from the docs; the plugin cache write; `emit_footprint --json` prints TSX; keeping a board's documents undocumented; repeated/NC pads undocumented.
