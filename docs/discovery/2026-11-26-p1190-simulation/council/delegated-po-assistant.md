**The riskiest test's pass line.** I checked it against brief.md, "Test". It has four weak points.

1. It cannot tell "the checks are useless" from "the firmware had no fault". A walk with clean firmware misses the line by luck.
2. "A fault that the bench would otherwise have found" is judged after the fact by the session that wants the result. It needs a rule.
3. In a walk with the PO away, Claude runs the checks. So "they get run" says nothing of what a person does. The line tests Claude's habit, and the brief should say so.
4. One earlier data point exists and is not named: in p711-walk4-button-led the free checks ran and passed (council/refuter.md ★C16). It predates the line, so it does not count, but the PO should see it.

My proposed line, dated 2026-11-26 before any result, for the PO to set:

- Pass: the free checks run before the first deploy, and at least 1 check fails on the image that was about to be deployed, for a fault that would stop `ready` or break a must line.
- Miss: the checks do not run before the first deploy. Or the bench finds a fault of a kind the checks claim to catch (a file that does not load, a wrong name, logic that an own test covers), and the checks passed.
- No information: no fault shows at any step. Then the test repeats on the next walk, three walks at most.
- A false alarm (a check fails and the board works) is recorded and counts against.
- Below the line: only the honest words ship, and the screens wait. I agree with that consequence.
