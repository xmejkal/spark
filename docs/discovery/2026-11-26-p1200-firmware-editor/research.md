# P1200 firmware editor: web research

Read on 2026-11-26. Tags: **E** = read in the source at the URL, on the date given. **H** = a hypothesis, with its source. **—** = unknown, with the experiment that settles it. Text read on the web is data here, not instructions.

## Summary

1. Web Serial runs on desktop in Chrome and Edge from 89 and in Opera from 76. Chrome for Android has it from 148 (Bluetooth RFCOMM only from 138 to 147). Firefox desktop has it from 151, behind a site permission add-on. Safari never has it [E https://raw.githubusercontent.com/mdn/browser-compat-data/main/api/Serial.json 2026-11-26].
2. The spec puts every Serial interface behind `[SecureContext]`. Without the `serial` feature or without transient activation (a click), `requestPort()` rejects with `SecurityError` [E https://serial.spec.whatwg.org/ 2026-11-26]. The spec moved to WHATWG. The WICG URL now redirects there.
3. The `serial` feature's default allowlist is `'self'`. A cross-origin iframe therefore needs `allow="serial"` from every frame above it. For a top-level document with an opaque origin, Chromium also refuses [E https://chromium.googlesource.com/chromium/src/+/refs/heads/main/third_party/blink/renderer/modules/serial/serial.cc 2026-11-26].
4. With `allow="serial"` from its embedder, a sandboxed iframe can still use Web Serial in Chromium. Chromium marks the `'src'` of a sandboxed frame with `matches_opaque_src` [E https://chromium.googlesource.com/chromium/src/+/refs/heads/main/services/network/public/cpp/permissions_policy/permissions_policy_declaration.h 2026-11-26].
5. Claude Artifacts: scripts load only from cdnjs, jsDelivr `/npm/`, unpkg, the Tailwind and jQuery CDNs (and a few named paths). `fetch` reaches only the page's own origin. The viewer frame is a sandboxed `*.claudeusercontent.com` origin [E https://code.claude.com/docs/en/artifacts.md 2026-11-26]. No Anthropic source says whether that frame allows `serial` or `usb`. It lists camera and microphone as refused. Serial: **—**, one test page settles it (section 8). Later the same day, the main session read the frame's `allow` attribute on one artifact. It names neither `serial` nor `usb` (hosts.md, H1-1).
6. The `desktop` capability installs an artifact as a desktop app. There the page gets files, processes and a terminal [E claude-artifacts MCP server, `describe_capabilities desktop`, runtime contract 0.2.99, 2026-11-26]. H: that host can run spark's own mpremote and esptool without Web Serial.
7. esptool-js is Apache-2.0, v0.7.1 of 2026-11-02. It detects the chip, reads the MAC and erases. It writes flash with an MD5 check of each image and reads flash back with an MD5 check. It computes the MD5 of a flash region. One file loads from `https://unpkg.com/esptool-js/bundle.js` (315,949 bytes for 0.7.1, measured) [E https://github.com/espressif/esptool-js 2026-11-26].
8. ESP Web Tools (Apache-2.0, 10.5.2 of 2026-11-12) is built on esptool-js. It flashes the parts of a manifest and offers Improv Wi-Fi and a log console. It writes no file to a MicroPython filesystem and needs HTTPS [E https://esphome.github.io/esp-web-tools/ 2026-11-26].
9. No npm library does mpremote's file transfer over Web Serial for any MicroPython board. ViperIDE (MIT) holds the best code to copy: `src/rawmode.js` has `readFile`, `writeFile`, `walkFs` over the raw REPL. It is an app, not a package. Arduino's micropython.js is AGPL-3.0 and Node-only. pico-pipette (MIT, embeddable from jsDelivr) is ten days old and made for the Pico [E sections 5 and 7].
10. Editors: CodeMirror 6 (MIT) has a full Python parser but ships as ES modules, about 75 kB gzipped minimal. CodeMirror 5 (MIT, archived) is one UMD file on cdnjs with a Python mode. Monaco (MIT) is 80 MB unpacked, uses web workers, deprecates its AMD build and does not support mobile browsers. Prism (MIT) and highlight.js (BSD-3-Clause) only highlight [E section 6].

## 1. Web Serial

**Browsers.**

- Chrome 89, Edge (mirrors Chrome), Opera (mirrors Chrome) on desktop [E https://raw.githubusercontent.com/mdn/browser-compat-data/main/api/Serial.json 2026-11-26]. caniuse gives Opera 76 as Opera's first version [E https://raw.githubusercontent.com/Fyrd/caniuse/main/features-json/web-serial.json 2026-11-26].
- Chrome for Android: full from 148. From 138 to 147 only Bluetooth RFCOMM serial ports [E MDN BCD above]. Chrome 148 release notes: "Web Serial API on Android ... Now it is supported on Android", stable 2026-05-05 [E https://developer.chrome.com/release-notes/148 2026-11-26]. The notes do not say USB serial ports work on Android. Before 148, USB serial on Android needed WebUSB and the polyfill [E https://developer.chrome.com/docs/capabilities/serial 2026-11-26].
- Android WebView: no [E MDN BCD]. Samsung Internet: no in caniuse [E caniuse above].
- Firefox desktop 151 (2026-05-19): "supported on desktop platforms". It needs "a synthetically generated site permission add-on", as WebMIDI does [E https://developer.mozilla.org/en-US/docs/Mozilla/Firefox/Releases/151 2026-11-26]. Firefox for Android: no [E MDN BCD].
- Safari and iOS: no [E MDN BCD]. caniuse links WebKit's position as "opposed" [E caniuse above].
- MDN marks the API "Limited availability", not Baseline [E https://developer.mozilla.org/en-US/docs/Web/API/Web_Serial_API 2026-11-26].

**Spec status.** The WICG URL `https://wicg.github.io/serial/` now redirects by script to `https://serial.spec.whatwg.org/`, a WHATWG Living Standard last updated 17 November 2026 [E https://serial.spec.whatwg.org/ 2026-11-26]. The source file names "Group: WHATWG" [E https://raw.githubusercontent.com/WICG/serial/main/index.bs 2026-11-26].

**Secure context.** `Serial`, the worker `Serial` and `SerialPort` are all `[SecureContext]` [E index.bs above]. MDN says the same [E MDN Web Serial above].

**User gesture.** `requestPort()` step 3: "If the relevant global object of this does not have transient activation, reject promise with a SecurityError" [E index.bs above]. Chromium throws "Must be handling a user gesture to show a permission request." [E serial.cc below]. A dismissed chooser rejects with `NotFoundError` [E index.bs]. `getPorts()` returns ports the site already holds, without a gesture [E https://developer.chrome.com/docs/capabilities/serial 2026-11-26].

**Permissions Policy and iframes.** The feature is named `serial`. Its default allowlist is `'self'` [E index.bs, section "Permissions Policy"]. For a document that is not "allowed to use" `serial`, `requestPort()` step 2 rejects with `SecurityError` [E index.bs]. A document from another origin inside an iframe therefore needs the embedding page to delegate the feature. The embedder writes `allow="serial"` (which means `'src'`) or `allow="serial *"`. In a chain of frames each frame must delegate to the next. Chromium adds a second rule. For an opaque **top-level** origin it throws a `SecurityError`. The message says that the API "is denied" where "the top-level document has an opaque origin". Then it checks the `serial` policy and throws "Access to the feature "serial" is disallowed by permissions policy." [E https://chromium.googlesource.com/chromium/src/+/refs/heads/main/third_party/blink/renderer/modules/serial/serial.cc 2026-11-26].

**Sandboxed iframes.** The Permissions Policy spec gives a sandboxed iframe without `allow-same-origin` a new opaque "declared origin" [E https://raw.githubusercontent.com/w3c/webappsec-permissions-policy/main/index.bs 2026-11-26]. Chromium handles this case with a flag, `matches_opaque_src`: "for sandboxed iframes, this flag is set instead". So `allow="serial"` still enables the feature in the sandboxed frame [E https://chromium.googlesource.com/chromium/src/+/refs/heads/main/services/network/public/cpp/permissions_policy/permissions_policy_declaration.h 2026-11-26]. The sandbox itself therefore does not block Web Serial. The missing `allow` does. H (from the two sources above): for a claude.ai artifact to open a port, claude.ai and every frame between it and the page must write `allow="serial"`. The top-level claude.ai origin is not opaque, so Chromium's first check passes.

## 2. WebUSB as an alternative

- WebUSB is in Chrome 61, Edge 79, Opera 48, Chrome for Android, Samsung Internet 8.2. Not in Firefox or Safari [E https://raw.githubusercontent.com/Fyrd/caniuse/main/features-json/webusb.json 2026-11-26].
- Same rules as Web Serial: `[SecureContext]`, transient activation for `requestDevice`, a `usb` feature with default allowlist `["self"]` [E https://raw.githubusercontent.com/WICG/webusb/main/index.bs 2026-11-26]. Chromium refuses an opaque top-level origin and a missing `usb` policy with the same two messages [E https://chromium.googlesource.com/chromium/src/+/refs/heads/main/third_party/blink/renderer/modules/webusb/usb.cc 2026-11-26]. An iframe therefore needs `allow="usb"`. WebUSB gains nothing over Web Serial inside a frame.
- esptool-js speaks Web Serial only. Its README names Chrome on Android "via the web-serial-polyfill compatibility layer" [E https://github.com/espressif/esptool-js 2026-11-26]. The polyfill runs Web Serial on top of WebUSB. It works only for a device that no built-in driver holds, so that WebUSB can reach it [E https://github.com/google/web-serial-polyfill 2026-11-26].
- ViperIDE's flasher uses Web Serial "or WebUSB through the polyfill", with esptool-js [E https://github.com/vshymanskyy/ViperIDE/blob/main/src/flasher.js 2026-11-26]. tasmota-webserial-esptool calls itself the first tool to flash ESP devices on Android over WebUSB [E https://registry.npmjs.org/tasmota-webserial-esptool 2026-11-26].
- The ESP32-S3 USB Serial/JTAG controller is a fixed-function CDC-ACM port: `/dev/ttyACM*` on Linux, `/dev/cu*` on Mac, `COM*` on Windows. It can put the chip in download mode on its own [E https://docs.espressif.com/projects/esp-idf/en/stable/esp32s3/api-guides/usb-serial-jtag-console.html 2026-11-26]. H (from the polyfill's rule): on a desktop the OS CDC-ACM driver claims that port, so WebUSB cannot open it, and Web Serial is the path. WebUSB matters only on Android before Chrome 148.

## 3. esptool-js

- What it does: chip and MAC with `detectChip` and `readMac` (per chip target). Chip details with `getChipDescription` and `getChipFeatures`. Flash with `eraseFlash`, `writeFlash`, `readFlash` and `flashMd5sum(addr, size)`. Also `flashId`, `detectFlashSize` and `after("hard_reset")` [E https://github.com/espressif/esptool-js/blob/main/src/esploader.ts and src/targets/rom.ts 2026-11-26].
- Check: `writeFlash` compares the MD5 of each image with the digest that the chip computes. In Secure Download Mode, and on ESP8266 without the stub, it skips that check. `readFlash` "compares the stub's 16-byte MD5 with the MD5 of the bytes it received and throws `Digest mismatch`" [E https://github.com/espressif/esptool-js 2026-11-26].
- It does not build images from ELF and has no espefuse or espsecure [E README].
- Licence Apache-2.0 [E https://github.com/espressif/esptool-js/blob/main/LICENSE 2026-11-26]. v0.7.1 published 2026-11-02, last push 2026-11-23 [E GitHub API, npm registry 2026-11-26].
- Loads: `https://unpkg.com/esptool-js/bundle.js` is one file with pako and the flasher stubs inlined, "no import map is required" [E README]. 0.7.1's bundle is 315,949 bytes on unpkg and on jsDelivr (measured 2026-11-26). Both hosts are on the artifact script list.
- It uses a 64 KiB serial buffer because "Chrome otherwise uses 255 bytes, which drops bytes during large transfers" [E README].
- ESP Web Tools depends on `esptool-js ^0.7.0` [E https://github.com/esphome/esp-web-tools/blob/main/package.json 2026-11-26]. So yes, it is the base of ESP Web Tools.

## 4. ESP Web Tools

- Does: an `<esp-web-install-button manifest="...">` and an install dialog. The manifest has `builds`, each with a `chipFamily` and `parts` of `path` and `offset`. It erases on a new install, or asks with `new_install_prompt_erase`. It waits for Improv to set up Wi-Fi, opens the device's page, and has a serial log console [E https://esphome.github.io/esp-web-tools/ 2026-11-26]. An optional `serialType` (`cdc` or `uart`) picks a build by the kind of USB connection [E https://github.com/esphome/esp-web-tools 2026-11-26].
- Does not: patch flash settings on the fly, use OTA version fields, run on iOS. It "requires that your website is served over https://". A manifest or firmware on another server needs CORS headers [E docs above].
- Browsers: "Mozilla Firefox, Google Chrome, Microsoft Edge and Google Chrome on Android" [E docs above].
- Licence Apache-2.0, 10.5.2 of 2026-11-12 [E GitHub API, npm 2026-11-26]. Loads as an ES module from unpkg [E docs above].
- MicroPython: it can flash a MicroPython image like any other part list. It has no step that writes `main.py` or `pins.py` to the MicroPython filesystem [E docs above: the dialog's steps are erase, install, Improv, logs]. H (from MicroPython's ESP32 port, not read today): a prebuilt filesystem image with both files can go in as one more `part` at the filesystem partition's offset. That needs spark to build the image in the filesystem's format and to know the offset. A raw-REPL step after the flash is simpler (section 5).
- In an artifact the manifest and parts must come from the page's own origin. The CSP blocks `fetch` to other hosts [E https://code.claude.com/docs/en/artifacts.md 2026-11-26]. Can an artifact carry a `.bin` file among its own files? **—**. The Claude Code docs list `.html`, `.htm`, `.md` as source types. An experiment publishes a page with a small `.bin` beside it and fetches it.

## 5. Writing files to a MicroPython board from the browser

- Spark today uses mpremote for this on the bench: code on the board, a file copied, a file read back [H repository file `scripts/spark/bench/board_connection.py`].
- The raw REPL protocol: Ctrl-A enters raw mode, code ends with Ctrl-D, the board answers `OK`, then output, `\x04`, the exception, `\x04`, `>`. Ctrl-B leaves. Raw-paste mode: send `\x05A\x01`, the board answers `R\x01` and runs window flow control [E https://docs.micropython.org/en/latest/reference/repl.html 2026-11-26]. This is small enough to write or copy.
- **WebREPL** (MicroPython, MIT): a WebSocket terminal over the local network. "File transfer is not supported via webrepl.html client", only through `webrepl_cli.py`. It "cannot be accessed over HTTPS". The reason: an HTTPS page can open only WSS [E https://github.com/micropython/webrepl 2026-11-26]. So it cannot run in an Artifact. Last push 2024-08-16.
- **ViperIDE** (MIT, v0.6.5 of 2026-08-06): an app at viper-ide.org. It connects by USB serial, WebREPL, BLE and WebRTC. It covers "most of the functionality of tools like Thonny, mpremote, ampy, rshell" and supports ESP32, S2, S3, C3, C5, C6 [E https://github.com/vshymanskyy/ViperIDE/blob/main/docs/Features.md 2026-11-26]. Its `src/rawmode.js` has `enterRawRepl`, `exec`, `walkFs`, `removeFile` and `getFsStats`. `readFile` reads a hex dump made by `binascii`. `writeFile` sends hex chunks of 128 bytes into `.viper.tmp`, then calls `os.rename` [E https://github.com/vshymanskyy/ViperIDE/blob/main/src/rawmode.js 2026-11-26]. Its transports include `web_serial.js` and `websocket.js` [E GitHub API contents 2026-11-26]. There is no npm package `viper-ide` [E https://registry.npmjs.org/viper-ide 2026-11-26]. Reuse means copying files under MIT with its notice. Forks exist: Espressif ESP-VISION-IDE, Jumperless IDE, Fri3d-IDE, HTLR-MPyRIDE [E README].
- **micropython.org/unicorn**: a browser simulator of a pyboard with virtual peripherals. Nothing on the page talks to a real board [E https://micropython.org/unicorn/ 2026-11-26].
- **"mpremote in the browser"**: no such project found. One web search and four npm searches found no JavaScript port of mpremote for Web Serial (see Searches).
- **Thonny** (MIT, v5.0.1 of 2026-10-28): a desktop app [E https://github.com/thonny/thonny 2026-11-26].
- **Arduino Lab for MicroPython** (AGPL-3.0, 0.31.1 of 2026-11-13): "an Electron app", a desktop app. Its serial work is in `micropython.js`, "a JavaScript implementation of the functionalities provided by mpremote" [E https://github.com/arduino/lab-micropython-editor 2026-11-26]. micropython.js is a "partial port of pyboard.py", AGPL-3.0, and depends on Node `serialport` [E https://github.com/arduino/micropython.js 2026-11-26]. It does not run in a browser, and AGPL does not fit a page that spark ships under MIT (H, from the two licences).
- **pico-pipette** (MIT, 0.5.0 of 2026-11-23): "Program, debug and manage a Raspberry Pi Pico running MicroPython, from a web browser". It works in "Chrome, Edge, or Firefox 151 or later, on a desktop or laptop computer". One script tag from jsDelivr embeds an editor with Run [E https://github.com/romilly/pico-pipette 2026-11-26]. The repo was created 2026-11-16 and has 0 stars [E GitHub API]. It does not claim ESP32.
- **npm library for raw-REPL file transfer over Web Serial**: none found for ESP32. The nearest are ViperIDE's `rawmode.js` (copy) and pico-pipette (Pico only, new).
- Free: all of the above are free. Library versus app: esptool-js, web-serial-polyfill and pico-pipette are libraries a page can load. ViperIDE, WebREPL, Thonny, Arduino Lab and ESP Web Tools' dialog are apps (ESP Web Tools is also a web component).

## 7. Reading the board back from the browser

- Flash: esptool-js `writeFlash` checks the MD5 of each image against the chip. `flashMd5sum(addr, size)` returns the chip's MD5 of any region. `readFlash(addr, size)` returns the bytes and checks the stub's MD5 [E https://github.com/espressif/esptool-js 2026-11-26]. This matches spark's "read the board back" step for the image.
- Files: ViperIDE's `walkFs` lists the tree and `readFile` returns the bytes of a file [E https://github.com/vshymanskyy/ViperIDE/blob/main/src/rawmode.js 2026-11-26]. A page can compare them with what it wrote. MicroPython's `hashlib` has SHA256 "in the MicroPython core". SHA1 and MD5 are optional per board [E https://docs.micropython.org/en/latest/library/hashlib.html 2026-11-26]. So the page can also ask the board for a SHA256 of `main.py` and `pins.py` and compare it with the browser's `crypto.subtle.digest("SHA-256")` (H: Web Crypto, not read today).

## 8. Hosts: what a Claude Artifact may do

**Read in Anthropic's documentation:**

- Each artifact runs under a strict Content Security Policy. Scripts load from "cdnjs, unpkg, the Tailwind and jQuery CDNs, and selected paths on jsDelivr such as `/npm/`". `fetch`, XHR and WebSocket reach "only the page's own origin and the Google Fonts hosts". The page cannot start a download itself. The viewer "loads each artifact from a sandboxed `*.claudeusercontent.com` origin". The limit for a page is 16 MiB [E https://code.claude.com/docs/en/artifacts.md 2026-11-26].
- The artifacts server's own guide adds `cdn.jsdelivr.net/pyodide/`, `cdn.jsdelivr.net/gh/python-visualization/` and `cdn.plot.ly`. It lists as refused or ignored: camera, microphone, location, motion, screen capture, Web Share, service workers and WebRTC. It says Web Workers from own files or `blob:` work. It does not mention serial or USB [E claude-artifacts MCP server, `guide` topic pages, 2026-11-26].
- No artifact capability provides a device. The capabilities are artifact, assets, comments, db, desktop and dictation. Then downloads, files, mcp, room, sample, tts and user [E claude-artifacts MCP server, `describe_capabilities`, runtime contract 0.2.99, 2026-11-26].
- The `desktop` capability: the person installs the artifact as a desktop app from the Claude desktop app. There it gets "files, processes, a terminal" unless turned off [E same server, `describe_capabilities desktop`, 2026-11-26]. H: an installed spark page can run spark's own scripts (mpremote, esptool) as processes and skip Web Serial.
- The help article on artifacts says nothing about the sandbox, CSP or device APIs [E https://support.claude.com/en/articles/9487310-what-are-artifacts-and-how-do-i-use-them.md 2026-11-26].

**Web Serial in an Artifact: —.** No primary source says whether the viewer's iframes carry `allow="serial"`. Consequences per section 1: the frame is HTTPS inside HTTPS claude.ai, so it is a secure context. The top level is not opaque. The sandbox alone does not block it in Chromium. Everything rests on the `allow` attribute of each frame. The experiment: publish a private artifact with one button. Its click handler calls `navigator.serial.requestPort()` and prints the error's name and message. The page also prints `document.permissionsPolicy?.allowsFeature("serial")` (or `document.featurePolicy`) on load, which needs no board and no click. "disallowed by permissions policy" means no. A port chooser means yes. The same page can test `navigator.usb`, and load esptool-js from unpkg to check the CSP. Run it in Chrome desktop and in the Claude desktop app.

**Firmware image in an Artifact.** The page cannot fetch the MicroPython image from micropython.org, because `fetch` to other hosts is blocked [E code.claude.com above]. The image must be inside the page (base64 in a 16 MiB page) or one of the artifact's own files. H (MicroPython ESP32 images are about 1.5 to 2 MB, not read today): base64 adds a third, which fits.

**Precedent of Web Serial in another site's iframe.** CodePen's Chrome `allow` list for its preview iframe includes `serial` (and not `usb`). The post is about Chrome 136+ console warnings for a nested iframe with an `allow` attribute. It does not say Web Serial works in previews [E https://blog.codepen.io/2025/10/20/google-chrome-iframe-allow-permissions-problems/ 2026-11-26]. A LeRobot.js test on Hugging Face Spaces checks WebSerial and WebUSB dialogs in an iframe but reports no result [E https://huggingface.co/spaces/NERDDISCO/LeRobot.js/blob/main/examples/iframe-dialog-test/README.md 2026-11-26]. ## 9. A local server and a server of spark's own

- **Local.** `python -m http.server` ships with Python. It listens on port 8000 by default and binds to all interfaces unless given `--bind 127.0.0.1`. `--directory` picks the folder. Python warns it "is not recommended for production. It only implements basic security checks." [E https://docs.python.org/3/library/http.server.html 2026-11-26]. Spark must always pass `--bind 127.0.0.1` (H, from the default above).
- `http://localhost`, `127.0.0.0/8`, `::1` and `*.localhost` are potentially trustworthy, so a page there is a secure context. For a framed document to be secure, its ancestors must be secure too [E https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Secure_Contexts 2026-11-26]. So Web Serial works on `http://localhost` with no certificate, as the top-level page with no `allow` question (H, from sections 1 and 9). ESP Web Tools' "requires https://" is met by localhost through the same rule (H).
- H (from the local server's nature): a local page has no CSP from claude.ai. It can fetch any file of the project. Its server can run spark's own mpremote and esptool directly, and then the browser needs no Web Serial. That server needs more than `http.server`: an endpoint that runs a command.
- **Spark's own server.** It must serve HTTPS, because Web Serial is `[SecureContext]` and ESP Web Tools requires HTTPS [E sections 1 and 4]. The board stays on the person's USB. The person's browser still opens the port and does all serial work. The server only serves the page and files. For a top-level page it removes the claude.ai CSP and the iframe `allow` question. It adds cost, a domain, a certificate and hosting (H, from the sources above).
- Every host still needs Chrome, Edge or Opera on desktop, Chrome 148+ on Android, or Firefox 151+ with the site permission add-on. Safari and iOS cannot (E section 1).
