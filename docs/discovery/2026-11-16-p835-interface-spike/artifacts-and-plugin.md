# P835 part 1: how a Claude Code plugin gives a person an interface (Artifacts first)

Read 2026-11-16 (Europe/Prague). Tags: D a source says it directly, E an experiment or a read of the runtime, H inference.
Runtime contract read: 0.2.96 (describe_capabilities, no argument).

## Q1 What the runtime says a page is for, capability by capability

- E: capabilities listed: artifact (formerly self), assets, comments, db, dictation, downloads, files, mcp, room, sample, tts, user. Source: describe_capabilities (no arg), 2026-11-16. Caveat: the list is per account and per contract version.
- D: a page is one HTML document in a sandboxed frame under a CSP; scripts inline or from listed CDNs; "fetch, XMLHttpRequest and WebSocket to other hosts are blocked"; no downloads by <a download>, no clipboard reads, no window.open for most viewers. Source: guide topic pages, 2026-11-16. Caveat: a capability can lift a limit (downloads).
- D: `db`: rows outside the page, "shared rows, per-person state, data Claude reads"; rules per path (view < interact < admin < owner); get/set/update/delete, where/orderBy/limit, onSnapshot; "No secrets; shared data is untrusted"; Claude seeds with db_write after publish. Fits spark: yes, it is the request/answer channel P829 already uses. Source: describe_capabilities db. Caveat: rows are not the truth; the project's files are.
- D: `artifact` (was `self`): the page republishes itself (`artifact.publish(html)`) and every open view reloads; "the page is the record". Fits spark: no; spark's truth is the project's files, and Python writes the page. Source: describe_capabilities artifact.
- D: `room`: "reaches whoever has the page open RIGHT NOW"; emit/on moments, presence, named rooms; "NOTHING persists and messages can drop". Also `sendToClaudeSession(data)` and `canSendToClaudeSession()`. Fits spark: the send half, maybe (see Q2); the broadcast half, no (one viewer). Source: describe_capabilities room, types:true. Caveat: the types are long; read in full below.
- D: `files`: "reads a Claude Code project's files as the viewer"; declared with `{files: {project: "chan_..."}}`; list/read/download; read lags a few seconds after an edit; "Only project members can publish an artifact declaring files"; "Don't copy file contents into the artifact's data". Fits spark: maybe, read-only, so the page could read build.json itself; whether a local (non-cloud) Claude Code project has a "chan_" id is not known. Source: describe_capabilities files. Caveat: not tried (brief step 5 not run).
- D: `mcp`: the page calls the viewer's claude.ai connectors, or `host:<name>` "for a local MCP server on the viewer's device (Claude app only; else server_not_connected)"; watchTool for display, callTool for an action; viewer consents. Fits spark: only in the Claude desktop app and only with a spark MCP server installed there; in a browser it answers server_not_connected. Source: describe_capabilities mcp. Caveat: the desktop app's local MCP servers are its own config, not Claude Code's.
- D: `sample`: the page asks Claude directly (memoryless; text or JSON; page-side tools; streaming through onText). Fits spark: no for the flow (it is a fresh model call, not the session that holds the project; it cannot run spark's scripts); maybe later for free-text help on a panel. Source: describe_capabilities sample. Caveat: costs the viewer's usage; consent on first call.
- D: `comments`: the page opens the shell's comment composer, or (full form) writes comments as the viewer; `sendToClaude` brings Claude into a thread. Watch/wake: "Only a cloud session can be woken" (watch tool description). Fits spark: no for clicks; a comment wakes a cloud session, not a local Claude Code. Source: describe_capabilities comments; watch tool description; brief Results step 6 (wake not_armed, no_address).
- D: `user`: who views (isOwner, canEdit, id). Fits spark: small; the page can hide buttons for a non-owner. Source: describe_capabilities user.
- D: `downloads`: the page offers a generated file, the viewer confirms. Fits spark: yes, later (the breadboard sheet or diagram.json as a file). Source: describe_capabilities downloads.
- D: `assets`, `dictation`, `tts`: uploads, speech to text, text to speech. Fit spark: not for the MVP. Source: describe_capabilities list.
- D: guide intent "other": seven types (Data, Design, Design System, Docs, Sheets, Slides, Whiteboard); a dashboard starts from the Data type. Fits spark: no type fits a flow page with offers; a plain page is right. Source: guide intent other. Caveat: the Data type could suit a later read-only status page.
- D: guide editorial: open viewers move to a new version "at their next quiet moment", keeping scroll; `window.claude?.hot?.snapshot` keeps script state across a republish. Fits spark: yes, P828's wiring step should survive a republish through hot.snapshot. Source: guide topic editorial.
- D: `files` reads "the Claude Code project the artifact declares" by an id `chan_...`, "with the viewer's own access"; 25 MiB per read; `asSampleTools` gives `sample` two read tools. Source: describe_capabilities files, types:true. H: a `chan_` id names a cloud (claude.ai) Claude Code session's project; a local Mac checkout has none, so `files` likely does not reach the local checkout Caveat: not tried; brief step 5 still open.

## Q2 Can a click reach or wake Claude without the person typing?

- D: "There is no way for a page to start Claude's turn by itself: the viewer's own Enter or their answer to the platform's dialog does." Source: describe_capabilities room, types:true, `sendToClaudeSession`. Caveat: the platform's own page types are exempt (their key press counts as the answer); a plain page like spark's is not one.
- D: `room.sendToClaudeSession(data, {deliver})`: from the viewer's click, hands a JSON object (4 KiB) to "THEIR Claude beside this page". "stage" (default) puts it in the composer as an attachment; "send" shows the platform's dialog, and the viewer's Send starts Claude's turn with the data as the message. Destinations: "pane" (a conversation open beside the page), "session" (a Claude session of the viewer's that has the artifact), "new" (a new conversation or the viewer's chat). Source: same. Caveat: "beside this page" means claude.ai or the Claude app; nothing says a terminal Claude Code session counts. H: a local Claude Code in a terminal is not "beside" a browser tab, so the page would see "no_session" or open a claude.ai chat, which is not the session that holds the project.
- D: `room` admits "the Claude Code session that published this page, as an agent peer (kind "agent")" only "when the server admits it (flag-gated, off by default)"; "its client batches what it hears and may drop moments ... it reads a digest, never a live stream"; "every other agent cannot connect (an agent otherwise narrates through db)"; it never joins a named room. Source: same. Caveat: the claude-artifacts MCP server lists no room tool in this session (ToolSearch, 2026-11-16), so this session cannot join; the flag is off.
- D: "NOTHING persists and messages can drop"; a late joiner's state belongs in a db doc. Source: describe_capabilities room. So room cannot carry a request that must wait while Claude Code is quit (D8, D13).
- D: comment wake: "Wake this chat when the user sends a comment to Claude ... Only a cloud session can be woken." Source: watch tool description, 2026-11-16; brief Results step 6 (every publish: wake not_armed, reason no_address). Caveat: a cloud Claude Code session (claude.ai/code) could be woken; spark's work needs the person's Mac (USB, store, drawer).
- H: so for a local Claude Code session there is no wake. The click waits in `db` until the person's next message (D8). The one thing that could help later is `sendToClaudeSession` with "stage" if the page is opened beside a claude.ai conversation, but that conversation is not the local session.
- D (new, changes Q2): a Claude Code mod (a plugin with a hooks module) can run a timer (`$.clock.every`) and start a turn: "`$.prompt.submit({ text })` ... The call waits until the session is idle and then starts a new turn." Claude reads the text "after a sentence that names your mod as the sender". `$.mcp.call` calls "a tool on a connected MCP server". Source: https://code.claude.com/docs/en/plugins/mods/api, read 2026-11-16. H: so a spark mod could poll the page's `db` through the claude-artifacts server every N seconds and submit "a page request waits" when the session is idle: a click then wakes an OPEN local session with no typing. Caveats: not tried; whether `$.mcp.call` may call a server the plugin does not list is not stated (`$.mcp.connect` is limited to the plugin's own servers); each woken turn costs tokens; a click while Claude Code is quit still waits (D13); after the person presses Esc, submits are refused until their next input.
- D: channels: "A channel is an MCP server that pushes events into a Claude Code session"; local stdio server; `notifications/claude/channel`; "Events queue into the session and are processed in order"; research preview; custom channels need `--dangerously-load-development-channels` because only the official allowlist loads. Source: https://code.claude.com/docs/en/channels-reference, read 2026-11-16. Fits spark: no for now; an Artifact page cannot POST to a local port (guide pages: fetch to other hosts blocked), and the dev flag is a heavy ask of a user. The mod timer does the same job with no flag.
- D: mods are on by default from Claude Code v2.1.287 (terminal) and v2.1.286 (Desktop app); hooks run in the terminal, Desktop Code tab, VS Code, `-p` and cloud sessions; drawing only in terminal, Desktop and VS Code. Source: https://code.claude.com/docs/en/plugins/mods/overview, read 2026-11-16. Caveat: an org admin can turn user mods off; a mod is unsandboxed code with the user's permissions.

## Q3 Streaming and SSE; a live channel; a page calling an outside URL

- D: the page cannot call out: "fetch, XMLHttpRequest and WebSocket to other hosts are blocked"; WebRTC, service workers, iframes of other sites refused. So a page cannot open an SSE stream (EventSource) to localhost or any server. Source: guide topic pages, 2026-11-16. Caveat: none found; this is the CSP.
- D: the live channels the runtime offers are `db` onSnapshot (persisted rows, pushed to open views) and `room` (moments and presence, nothing persisted, may drop). Source: describe_capabilities db and room. E: onSnapshot showed Claude's rows on the open page in under 1 s (brief Results step 2, 2026-11-15).
- D: `sample` streams Claude's answer to the page (`onText({text, delta})`). Source: describe_capabilities sample. Caveat: a fresh memoryless model call, not the session that runs spark.
- D: the publishing session in `room` "reads a digest, never a live stream: send it summaries, not streams". Source: room types.
- H: so live progress for a long build is possible only as rows: spark (or Claude) writes a progress doc (stage, status, Prague time) with db_write at each stage, and the page's onSnapshot shows it within a second. That costs one Claude tool call per update unless a mod or a script writes it; no spark script can write `db` itself (db_write is a claude-artifacts MCP tool behind the claude.ai login). Spark's stages take seconds (build is "seconds, no agents"), so per-stage rows are enough; SSE has no place.
- D: MCP itself still lists SSE as a deprecated transport; streamable HTTP replaced it (MCP spec 2025-03-26). Caveat: from memory of the spec, not re-read today; irrelevant to spark, which would use stdio.

## Q4 Claude Code's own plugin surfaces for an interface

- D: plugin components: skills, commands (prefer skills), agents, hooks (hooks/hooks.json), MCP servers (.mcp.json, stdio servers get CLAUDE_PLUGIN_ROOT, CLAUDE_PLUGIN_DATA, CLAUDE_PROJECT_DIR), LSP servers, output styles, workflows, experimental themes and monitors, `bin/` on the Bash PATH, `userConfig`, channels. Source: https://code.claude.com/docs/en/plugins-reference (redirects to the manifest reference), read 2026-11-16. Caveat: `bin/` keeps a plugin out of claude.ai and Cowork installs.
- D: a plugin's settings cannot set the main status line ("Only agent and subagentStatusLine take effect"); a mod's `$.ui.status(text)` puts one line under the prompt instead. Sources: WebSearch summary of the plugins reference, 2026-11-16 (not re-read on the page itself); mods api page.
- D: monitors: "Shell command Claude Code runs as a persistent background process", described "in the task panel and notification summaries"; `when: on-skill-invoke:<skill>`; they don't start with `-p`. Source: manifest reference. H: a monitor event reaches Claude, but the mods api page says monitor events before the user's next input after an Esc are dropped; a monitor is a weaker wake than a mod's `$.prompt.submit`.
- D: mods draw "a pane beside the transcript or a band above the prompt, with tabs, buttons, and text fields" in the terminal, the Desktop Code tab and VS Code; commands that run "at once, with no Claude turn, even while Claude is working"; `$.process.run`, `$.fs`, `$.http.fetch`, `$.mcp.call`, `$.clock.every`, `$.prompt.submit`. On by default from v2.1.287; this Mac runs 2.1.311 (`claude --version`, 2026-11-16). Source: mods overview, api and reference pages, read 2026-11-16. Fits spark: yes, as a second renderer of the same `flow.py show --json` (a "flow" pane with the phase rail and the four offers as buttons that run `flow.py run-request`), and as the waker for page clicks. Caveat: a mod is JavaScript in the plugin (spark is Python plus one bun tool), not sandboxed, and an org can switch user mods off; Elements are terminal-like (Text, Box, Button, Input, Image in terminal only), no HTML, so the schematic and breadboard views stay on the page.
- D: MCP Apps (SEP-1865, Final; `ui://` resources, `text/html;profile=mcp-app`, sandboxed frame, `app.callServerTool` from the UI) render in claude.ai and the Claude desktop app; "Claude Code calls the tool as text and doesn't render the UI"; a URL-added server is reached "from Anthropic's infrastructure", so localhost is not reachable; a local server renders only through the desktop app's config file. Source: https://claude.com/docs/connectors/building/mcp-apps/quickstart, read 2026-11-16; https://blog.modelcontextprotocol.io/posts/2026-01-26-mcp-apps/ (search result only). Fits spark: not now; it needs the person to use Claude Desktop chat (not Claude Code) with spark as a local MCP server, a second front door.
- D: settings hooks (UserPromptSubmit, SessionStart, etc.) run a script on an event and can add context; they cannot draw. Source: mods overview comparison table. H: a UserPromptSubmit hook could read waiting page requests and add them as context on the person's next message, so Claude never forgets to read `db`; but a settings hook cannot call an MCP tool, so it could only say "check the page" (it cannot read `db` itself). Cheap fallback if mods are off.
- D: output styles change how Claude writes replies; no UI. Source: manifest reference. Fits spark: no.

## Q5 MCP or none

- D: an Artifact page reaches MCP only through the `mcp` capability: the viewer's claude.ai connectors, or `host:<name>` "for a local MCP server on the viewer's device (Claude app only; else server_not_connected)"; viewer consent; `callTool` for an action, `watchTool` for display. Source: describe_capabilities mcp, 2026-11-16. H: so a page opened in the Claude desktop app could call a local spark MCP server's `run_request` tool directly and act at once, with no Claude turn; in a browser tab it cannot. Caveat: not tried (brief step 7); the server must be in the desktop app's own MCP config, not only in Claude Code's plugin; unknown whether the Code tab's plugin servers count as `host:` servers.
- D: Claude Code renders no MCP App UI; it uses MCP tools as text. Source: claude.com MCP Apps quickstart, 2026-11-16.
- D: a plugin can ship a stdio MCP server in `.mcp.json` with `${CLAUDE_PLUGIN_ROOT}`; it connects while the plugin is on. Source: manifest reference. Spark already ships two third-party servers this way (.mcp.json: espressif-docs, jlcpcb).
- D (spark's own record): "It adds typed schemas the host validates, structured output, and reach to hosts with no shell (Claude Desktop, claude.ai through `host:`, MCP Apps ...). It costs a running process and tool definitions in every session. Build it when a named host cannot run a shell ... and not before the catalog covers every operation." Source: docs/discovery/2026-10-19-p323-target-architecture/council/ai-interface.md section 8.
- H: for Claude Code alone an MCP server adds little over `flow.py ... --json` through Bash: Claude already runs the scripts, and the Operations already carry schemas. It would add tool definitions to every session's context. The new facts from this spike do not change the rule; they name the first host that would need it: the Claude desktop app, for a page click that acts at once through `host:spark`, or for an MCP App. Neither is the MVP.
- H: a spark mod is the cheaper answer to "a click should not wait for my typing": it needs no MCP server of spark's, it calls the claude-artifacts server Claude Code already has (to be checked), and it wakes the open local session.

## Q1 additions (design and diagrams topics)

- D: "Nothing on this server renders Mermaid or DOT source: left as it is, it shows as plain text. Draw the SVG instead." Source: guide topic diagrams, 2026-11-16. Matters for P826: a MermaidDiagram value reaches the page only if Python draws it as inline SVG, or the page loads a renderer from a CDN, which D7 forbids ("loads nothing from the web").
- D: the page renders in the viewer's theme (`data-theme` dark or light, or prefers-color-scheme); define tokens for both. "Complete at rest": everything readable once loaded, no wait for a click. Tools: "Encode state in form as well as in numbers (a pill, a chip, a severity stripe)". Source: guide topic design. Fits spark: P827's static HTML and its status word plus glyph already match; P827 must carry the two-theme tokens.

## Recommendation (H)

1. The page is a renderer and a request form, nothing more: Python writes it, `db` carries requests and answers, the project's files stay the truth (keep the MVP plan as it is).
2. Claude Code on the person's Mac stays the only actor. No click acts by itself. Do not use `sample`, `artifact.publish`, `files` or `host:` MCP for the MVP.
3. The new piece is a small spark mod (later card): a timer reads waiting requests and calls `$.prompt.submit` when the session is idle, so a click acts within seconds while Claude Code is open; with Claude Code quit, the click waits (D13). It can also draw a flow pane in the terminal from `flow.py show --json`.
4. Live progress = per-stage rows in `db` written by the session, shown through onSnapshot. No SSE: the page cannot open any connection out.
5. MCP: no spark MCP server now. Build it only when a named host has no shell: the Claude desktop app (`host:spark` from the page, or an MCP App). Keep ai-interface.md section 8 as the rule.
